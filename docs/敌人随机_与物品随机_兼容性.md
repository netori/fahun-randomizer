## 结论先说

**数据层兼容；方案层从 2026-10-22 19:1x 起有一个「物品 + 敌人一次写」入口，不必再点两次。**

- 两套随机器改的是不同的表/文件：
  - 职业物品随机：`EquipParamGoods` 等物品参数 + `GoodsCaption` 说明书 FMG，写 `mod\regulation.bin` 与 `mod\msg\zhocn\item_dlc02.msgbnd.dcx`；
  - 敌人 v1：`NpcParam` / `NpcThinkParam` / `MaterialExParam` + MSB 地图 + EMEVD，写方案层里的 `regulation.bin`、`map/MapStudio/*.msb.dcx`、`event/*.emevd.dcx`。
  - 没有同一张 param 表、同一行 ID、同一份 FMG 的争用；敌人层也不会删物品行。
- 但 YAFSML 的 `Plan=` **一次只认一个方案层**。历史上物品写入和敌人 v1 是两条独立写盘路径：物品写入会自动生成并挂载一个“只含物品”的层；敌人 v1 部署会生成并挂载一个“含敌人（以及当时本体里的物品改动）”的层。后挂的会把先挂的顶掉。
- **一次写入入口**（底部按钮文案变成「开始随机物品和敌人」时）把两条路径串成一次操作：
  1. 物品先写进本体（并同步说明书），**不导出物品层**；
  2. 敌人 v1 读这份已经含物品改动的本体，构建敌人层；
  3. 只挂这一个同时含物品与敌人的层。
  失败时 `native_deploy.deploy` 会把本体与 `Plan=` 一起回滚，不会留下半套。
- 仍要注意：只勾物品时产出的层只有物品；它会顶掉已挂的敌人层。要同时写，就把敌人页签的勾也留着，用「开始随机物品和敌人」。

## 推荐：一次写入（2026-10-22 起）

1. 先在「职业物品随机」页点「① 生成随机方案」（**不要**先点物品页的「写入游戏」）。
2. 到「敌人随机」页选预设/种子，点「①+② 物品+敌人一次写」。
   - 内部顺序是「物品写本体 → 敌人从这份本体建层 → 挂载」；日志里会看到 `[合并]` 前缀。
   - 最终只有一个方案层；层里 `regulation.bin` 同时含物品与敌人改动，地图/事件也在同一层。
   - 说明书由本体 `item_dlc02` 提供（敌人层不带 msg，引擎会读本体那份）。
3. 完全退出游戏再进。此时物品与敌人都在生效。

## 手动两步（旧路径，仍可用）

1. 先在「职业物品随机」页生成并点「写入游戏」；
   - 这会复原本体、写物品、生成物品层并**自动挂载**它；此时敌人随机不在这个层里。
2. 再到「敌人随机」页选预设/种子，点「② 部署到方案层」；
   - `enemy_write.build` 读的是**当前本体** `mod\regulation.bin`（已经含物品改动），所以新敌人层里的 regulation 同时含物品 + 敌人；
   - 地图/事件进同一层；说明书仍由本体 `item_dlc02` 提供（敌人层不带 msg，引擎会读本体那份）；
   - 部署完成后点「用这个方案玩」挂载这个敌人层。
3. 完全退出游戏再进。此时物品与敌人都在生效。

## 错误顺序（只点独立按钮时会“看起来敌人消失了”）

- 先部署敌人 v1，再点物品「写入游戏」：
  - 物品写入会复原本体并生成**只含物品**的新层，自动挂载它；
  - 敌人层没有被删，但 `Plan=` 已指向物品层，所以敌人随机不生效。
  - 用一次写入按钮不会走到这里。
- 这时如果手动把旧敌人层重新挂回去：
  - 旧敌人层的 regulation 是**物品写入之前**的快照，会把新物品改动遮住；
  - 本体的说明书却可能已经是新物品的，出现“说明书说随机了、实际没随机”的错位。
  - 不会损坏存档或文件，但状态不自洽。

## 怎么避免踩坑

- 想同时写：用敌人页的「①+② 物品+敌人一次写」；不要先点物品页「写入游戏」。
- 只想改物品：先物品写入，然后必须重新点一次敌人 v1「部署到方案层」，否则敌人会暂时消失；或者直接用一次写入。
- 只想改敌人：直接部署敌人层；不要再动物品页。
- 不确定当前层是否过期：`python investigation/apply/enemy_write.py --verify 敌人v1_区域缩放_物品+敌人_种子20261010_1022_2325` 会复算；manifest 的基线 hash 与本体不一致时会报出来。
- 想彻底回原版：物品页「还原成原始」会复原本体并清掉 `Plan=`，两层都不再生效。

## 实测（2026-10-22 17:3x）

- 读 19:4x 旧合并层 `敌人v1_物品+敌人_种子20261010_1022_1942`（该表是当时的验证记录；23:3x 的新层同样只改三张敌人表）与本体 regulation：除 `NpcParam` / `NpcThinkParam` / `MaterialExParam` 外，**其余条目逐字节相同（差异 0）**。本体相对原始备份有 2 个物品表变化（`ItemLotParam_map` / `ItemLotParam_enemy`），层里原样保留。也就是说：敌人层只改敌人相关的三张表，物品侧的任何参数改动只要在本体里，就会原样保留在层里。
- **合成测试**：在一份临时 regulation 的 `EquipParamGoods.param` 末尾改一个哨兵字节，再用 `enemy_write.build(plan_path=敌人v1_seed1 的计划快照, base_reg=临时 regulation, limit=1)` 构建一层；层里的 `EquipParamGoods.param` 与哨兵逐字节一致，且其余非敌人表差异 0。真实本体/方案层未参与，临时目录已删。
- **一次写入整层测试（2026-10-22 19:2x）**：同一份临时 regulation 加哨兵后走 `native_deploy._merge_enemy_layer`（`limit=1`、`mount=False`、临时 `out_root`），层里哨兵保留、`NpcParam` 已变、非敌人表差异 0，步骤记录 `plan_layer` + `enemy_merge`；临时目录已删。真实本体/方案层/`Plan=` 均未动。
- 当前层的目录里只有 `regulation.bin` + `map/MapStudio/*.msb.dcx` + `event/*.emevd.dcx`，没有 `msg/`；物品说明书由本体 `mod/msg/zhocn/item_dlc02.msgbnd.dcx` 提供。
- 本体 `regulation.bin` 的 SHA256 是 `a1a23462…b58e`，与当前层 manifest 的 `base.regulation_sha256` 一致，说明这一层就是拿当前（已写物品的）本体构建的。
- 所以“数据冲突”可以排除；“层被顶掉/说明书错位”是唯一的兼容性风险，靠部署顺序规避。
