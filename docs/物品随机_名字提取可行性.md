> 性质：**只做验证、不改代码**。结论用本机一次性实测得出，命令可复现；正文只留几条样例，不落整表。
> 背景：`docs/物品随机_范围扩展_讨论稿_20261023.md` §3.5 记录 weapon 0/750、accessory 0/6、gem 0/119 没有中文名，

## 1. 名字表在哪（实测事实）

容器：`法魂mod V3.0.3 …/mod/msg/zhocn/item_dlc02.msgbnd.dcx`，**304,511 B，78 张 FMG**。
同目录还有 `menu_dlc02.msgbnd.dcx`（505,503 B，菜单文本，不含物品名）；`mod/msg/` 下 **15 种语言**各有一份同名容器（`araae…zhotw`）。

| FMG（容器内名） | 字节 | 解析条目 | 去掉 `[ERROR]` 占位后 |
|---|---|---|---|
| `WeaponName.fmg` | 188,548 | 5,316 | **4,333**（滤掉 983） |
| `WeaponName_dlc01.fmg` | 28,624 | 751 | 751 |
| `WeaponName_dlc02.fmg` | 84 | 1（"DLC dummy"） | 1（假数据） |
| `GemName.fmg` | 7,428 | 227 | **101**（滤掉 126） |
| `GemName_dlc01.fmg` | 1,044 | 25 | 25 |
| `AccessoryName.fmg` | 9,368 | 173 | 173 |
| `AccessoryName_dlc01.fmg` | 3,484 | 40 | 40 |

三条结构事实（都影响实现，别踩）：

1. **`[ERROR]` / `%null%` 占位必须过滤**。`WeaponName` 5,316 条里 983 条是 `[ERROR]`，`GemName` 227 条里 126 条是
   `[ERROR]` —— 不滤就会把「武器名 = [ERROR]」写进界面（现有 `item_world_stats.names_from_xml()` 也是这么滤的）。
2. **DLC 名字是分开的文件，而且必须合并**：池内 627 把真武器里 **106 把只在 `_dlc01` 里有名字**
   （例：`1500000 左手匕首`），另有 3 把两边都有。只读 `WeaponName.fmg` 会漏掉这 106 把。
   `_dlc02` 在本基线是 84 字节的 dummy（唯一一条 `DLC dummy`），**不要**把它当第三张真表。
3. id 不是「一条记录一个 id」而是**区间**（FMG v2：一条记录 = `[下界, 上界]` + 槽号），
   `enemy_names.parse_fmg()` 已按区间展开，并且是按**槽号**取文本 —— 直接用它对，别自己重写。

## 2. 实测（命令 + 输出）

### 2.1 复现命令

探针只落临时目录（`%TEMP%\gf_names_probe.py`），不写仓库、不动游戏/法魂目录：

    import os, sys
    APPLY = r"...\随机mod\investigation\apply"
    sys.path.insert(0, APPLY)
    os.environ["CONVERGENCE_MOD_ROOT"] = r"...\法魂mod V3.0.3 汉化本体（…）"
    import native_guide as ng, enemy_names as EN

    p = os.path.join(os.environ["CONVERGENCE_MOD_ROOT"], "mod", "msg", "zhocn", "item_dlc02.msgbnd.dcx")
    bnd, _h, _raw = ng.read_msgbnd(p)                       # DCX(KRAK) -> BND4 -> [(内部名, 字节)]
    blobs = {os.path.basename(n.replace("\\", "/"))[:-4]: b for n, b in bnd.files}
    bad = ("[ERROR]", "%null%", "")
    clean = lambda d: {k: v for k, v in d.items() if v and v.strip() not in bad}
    weapon = clean(EN.parse_fmg(blobs["WeaponName"]))
    weapon.update({k: v for k, v in clean(EN.parse_fmg(blobs["WeaponName_dlc01"])).items() if k not in weapon})

运行（实测）：

    "C:\Program Files\Python312\python.exe" %TEMP%\gf_names_probe.py

计时：**读容器 0.01 s，解析 10 张 FMG 0.024 s，端到端（读+解析+合并）0.029 s** —— 完全可以在启动时现抽，
不必预先落盘。

| 类别 | 池内 id | EquipParam 里真有 | 有中文名 | 说明 |

| protector | 844 | 844 | **841** | 缺 3（99.6%，一致） |

## 3. 现有 GoodsName / ProtectorName 从哪来（问答 4）

链路（可点开复核）：

1. **源容器**：法魂 `mod/msg/zhocn/item_dlc02.msgbnd.dcx`（就是本文这一份）。
2. **抽出 .fmg**：`investigation/randomization-catalog/inputs/fmg/*.fmg` —— 只剩 14 张（`GoodsName.fmg 81,632 B`、
   `ProtectorName.fmg 30,064 B` 等），字节数与容器内同名 FMG **完全一致**。
3. **FMG → XML**：WitchyBND 3.0.1.0 的 `-u -p`，命令记在
   `investigation/randomization-catalog/logs/001_xml_ProtectorName.command.json`（`-- … inputs/fmg/ProtectorName.fmg`），
   产物在 `investigation/randomization-catalog/evidence/xml/*.fmg.xml`。
4. **读 XML 的地方**（这就是「现有物品名来源」）：
   - `investigation/randomization-dryrun/scripts/build_class_basis.py:133-135`（`fmg_names(...)` 读 `evidence/xml/GoodsName(.dlc01)`）
   - `investigation/randomization-dryrun/scripts/analyze_shops.py:30-35`
   - `investigation/apply/item_world_stats.py:200-206`（覆盖率就是在这里算的，weapon/accessory/gem 三栏**硬编码为 0**）

**同源验证**：用本文方法现抽 `GoodsName`/`ProtectorName`，与现有 XML **逐条全同名** ——
`GoodsName` 2,276/2,276、`ProtectorName` 724/724、两侧差集 0；覆盖率复算 1,535/1,614、841/844 与讨论稿一致。
=> 现有 XML 与「从 msgbnd 现读」是同一份数据，只是中间多了一道 WitchyBND。

**一个已存在的坑**：`WeaponName*.fmg.xml` 从来不在 `evidence/xml` 里 —— 它在
`investigation/weapon-baseline/evidence/xml/`，而该目录**已被删除**（`investigation/` 下已无 `weapon-baseline`）。
于是 `item_world_stats.py` / `update_guide.py` / `fix_guide.py` 里那些 `WB/evidence/xml/WeaponName.fmg.xml` 路径
现在都是死路径（真跑到就会 `FileNotFoundError`）。这也是「weapon 0/750」的直接原因，不是数据不存在。

**新三张能否同法**：能，而且比 WitchyBND 那条路更省事 —— 不用 ConPTY、不用外部 exe，直接
`read_msgbnd` + `parse_fmg`（`enemy_names.py` 读 `NpcName`、`boss_healthbar.py` 读 `GoodsName` 用的就是这套，
已在生产路径上跑过）。若想沿用「XML + `names_from_xml`」的旧形状，也只需自己写 10 行 XML 发射器，
产物约 246 KB（三张全表）。

## 4. Data0 路线：现状与代价（问答 1、2）

### 4.1 `er_data.py` 能做到哪一步

`investigation/apply/er_data.py`（140 行）实际只提供：

- `decrypt_bhd(path, pem)` —— 逐 256 B 模幂，**必须有 `DataN.pem`**
- `parse_bhd(plain)` —— 头 + 桶 + 条目 `{hash, size, padded, offset, aes{key, ranges}}`
- `load_dict(hash_txt)` / `path_hash(path)` —— **必须有 `Hash/DataN.txt`**
- `main()` —— 只打印「明文多大 / 版本 / 词典几条」，**没有取文件**

**缺的正是「按路径取文件」**：`.bdt` seek + 按区间 AES-CBC 解密 + DCX 解压（KRAK 还要 `oodle`），约 60 行；
外加一个 `get(path) -> bytes` 的入口。也就是说，即使密钥齐全，**现有代码也不能直接取出 msg**。

### 4.2 实测：本机跑不了（而且是静默失败）

    > "C:\Program Files\Python312\python.exe" investigation\apply\er_data.py
    游戏目录: F:\game\studygame\elden ring\ELDEN RING\Game
    钥匙目录: C:\Users\20905\AppData\Local\Temp\binderkeys\EldenRing_PC
    exit=0

`%TEMP%\binderkeys\EldenRing_PC\{Key,Hash}` **两个目录都是空的**（`Get-ChildItem` 零文件），
于是 `main()` 里 `os.path.isfile(pem)` 全不成立 → 全部 `continue` → **一条归档信息都不打印、退出码 0**。
这是「静默 no-op」，不能当成功读；`er_bhd_align.py` 同样会在此处 `FileNotFoundError`。
另外：`tools/witchybnd-3.0.1.0/WitchyBND.exe` 里也**没有**内置密钥（扫过 `BEGIN PUBLIC KEY` / `EldenRing_PC` / `GR_other`，均未命中），
它和 Nuxe 一样要外部 BinderKeys。本会话网络不可达（`raw.githubusercontent.com` 解析到非公网 IP），
所以「下载 BinderKeys」这一步在本环境无法验证。

### 4.3 更关键：名字要跟玩家实际加载的那一份一致

法魂的表里有**它自己追加的条目**：`WeaponName_dlc01` 751 条（`1500000 左手匕首` 这类）、`GemName_dlc01` 25 条
（`200000 战灰：落叶旋风脚`），id 一直排到 **6,950 万段**（`69500000 流纹万器`、`68510000 红熊爪`）；
池内 627 把真武器里 **458 把**落在 2,000 万段以上。Data0 是**游戏本体**归档，**一定没有**法魂追加的那些条目；
至于高段位的本体条目在 Data0 里叫什么、有没有，本机没有词典，**无法验证**。
=> 从「界面显示的名字 = 游戏里看到的名字」出发，msgbnd 是唯一正确的源；Data0 最多算「法魂没装 / 换语言」时的补充，
为它单独写 BHD5 提取器不划算。

### 4.4 未证实项（如实写）

`docs/本体归档解锁记录.md` 明说「条目表（bucket entry）的字段顺序还没对」，而 `parse_bhd()` 的
`stride=0x28 / AES 区间在 aes_off+16..` 只是代码注释里的断言，仓库里**找不到任何一次成功抽取的记录**
（无产物、无日志、无 CSV）。所以「Data0 能不能读通」目前是**未验证**，不是「已就绪」。

## 5. 建议做法（只写方案，本次未动代码）

1. **新模块** `investigation/apply/item_names.py`（GUI 用 `sys.path.insert(…, "investigation/apply")` 动态导入，
   放这里天然可被 `randgui.py` 用）：
   - `load_all(mod_root=None)` → `{"WeaponName": {...}, "WeaponName_dlc01": {...}, …}`
   - `merged(kind)` → base + `_dlc01` 合并，**冲突要逐条返回**（照 `enemy_names.merge_names()` 的纪律，别默默覆盖）
   - 内部：`native_guide.read_msgbnd` → `enemy_names.parse_fmg` → 过滤 `[ERROR]`/`%null%`
   - 缓存：`temp/` 或 `plans/` 下一份 JSON，**用 msgbnd 的 sha1 当失效键**（该文件会被说明书管线重写，见 §6）
2. **产物形态**：优先**运行时现抽**（0.03 s、跟随玩家版本、不用随包分发数据）；
   想给 spoiler log / 未来界面留离线件，就只存**池内 751 条**（20.1 KB JSON，实测），别存 5,398 条全表。
3. **自检**（可断言，数字取自本文实测）：gem 119/119、accessory 6/6、weapon 626/627；`23055000` 允许缺。
4. **池子口径**：先按 `EquipParam*` 剔掉悬空 id，再接名字 —— 否则界面会出现 123 条「（无名）」；
   这条与讨论稿 §3.2「认不出的 id 必须跳过」是同一件事。

## 6. 不确定项 / 风险

- **单基线**：只验了「法魂 V3.0.3 汉化本体（适配 1.17.1）+ 该 mod 的 zhocn 容器」。换法魂版本、换语言（`engus` 等 14 种）未测；
  代码上退路是「zhocn 优先，缺了退 engus」，但未实测。
- **容器会被本仓库改写**：`native_deploy` / `pipeline_deploy` 会重打包 `item_dlc02.msgbnd.dcx`（只改 `GoodsCaption`）。
  实测当前文件与 `apply/backup/…orig_20261011_095021` 相比：`WeaponName` / `WeaponName_dlc01` / `GemName` /
  `AccessoryName` 四张 **sha256 前 12 位完全相同**，只有 `GoodsCaption` 不同 => 名字表不受影响，但缓存仍应按 sha1 失效。
  另外当前容器 304,511 B、原始 366,164 B（说明书改写后变小），说明**字节数不能当版本标识**。
- **`23055000` 无名字**（真行、数字行名），需要「未知武器 #id」兜底；同理未来法魂新增物品可能先有行、后有名字。
- **accessory 计数口径**：讨论稿写 5，实测池内 6 个 id（1 个悬空但有名字）；对外表述要统一，否则覆盖率会「对不上」。
- **Data0 结论的上限**：本文只证明「现在不能直接用、也不需要」；**没有**证明「BHD5 布局一定错」——
  因为密钥缺失，连一次真实解析都没跑成。
