> **取证范围**：只读取证。分析对象是未随机化的法魂原始参数表 —— 当前 `mod/regulation.bin` 与 `investigation/apply/backup/regulation.bin.orig_20261011_080825` 逐字节相同（sha256 前 16 位 = `7bcd46b957ac49cf`，2,984,544 B），所以下面所有 param 行都是**未随机化**状态下的真值。

## 第 0 节 结论

**可以换 —— 换人之后，这个位置的露滴残渣 / 黄金精华照样掉。置信度：高（≈0.9）。**

一句话机制：奖励由**地图事件**（`common_func` 的 `90005875` 模板）按 **MSB entity id** 触发，批次号由每张地图的脚本以**字面量**写死；守卫自己的 `NpcParam` 行 `itemLotId_enemy` / `itemLotId_map` 全是 **-1**，且没有任何 `NpcParam` 引用这些批次 —— 也就是说奖励链上**根本没有 npc id 这一环**。随机器换的是 MSB 里该实体的 `npc_id/chara_id/model`，entity id 与 EMEVD 都不动，所以「谁站在那儿」不影响「掉什么」。

三条正证/否证（详见第 2 节）：

1. **正证**：`mod/event/common_func.emevd.dcx.js:7826-7840` 的 `90005875` 里，授予动作是 `AwardItemsIncludingClients(X4_4)`，击杀条件是 `WaitFor(CharacterDead(X0_4))` —— 两个参数都是**位置量**（entity id / 批次 id），没有 npc 参数。
2. **否证①**：25 个主条目的守卫 `NpcParam` 行，`itemLotId_enemy = -1`、`itemLotId_map = -1`、`getSoul = 0`；反过来，全表 1384 条 enemy 掉落引用 + 62 条 map 掉落引用里，**没有一条**指向 23 个授予批次中的任何一个。
3. **正证**：27 个 `90005875` 调用点分布在 27 张地图脚本里（每图恰好一条），批次号 24 个是 5 位数、3 个是 10 位数；这些批次在 `ItemLotParam_map` 里都实存，内容是 `1295 黄金精华` 或 `20900–20904 …灵药遗物`（见 2.3）。

**边界**：会变的不是奖励，而是别的 —— 血条名会错配（4.3）、守卫行的卢恩（`getSoul=0`）会变成新敌人的额度（4.5）。那是观感/数值问题，不是「奖励掉了没掉」的问题。

## 第 2 节 奖励授予机制的证据链

### 2.1 授予模板 `90005875 "Custom Boss Death Event"`（逐字）

`mod/event/common_func.emevd.dcx.js:7826-7840`：

~~~text
7826: // Custom Boss Death Event
7827: $Event(90005875, Restart, function(X0_4, X4_4, X8_4) {
7828:     EndIf(EventFlag(X0_4));
7829:     WaitFor(CharacterHPValue(X0_4) <= 0);
7830:     WaitFixedTimeSeconds(4);
7831:     SetBossBGM(X8_4, BossBGMState.Stop1);
7832:     SetBossBGM(X8_4, BossBGMState.Stop2);
7833:     PlaySE(X0_4, SoundType.SFX, 888880000);
7834:     WaitFor(CharacterDead(X0_4));
7835:     HandleBossDefeatAndDisplayBanner(X0_4, TextBannerType.EnemyFelled);
7836:     AwardItemsIncludingClients(X4_4);
7837:     SetSpEffect(10000, 3450);
7838:     SetEventFlagID(X0_4, ON);
7839:     EndEvent();
7840: });
~~~

三个参数**全是位置量**：`X0` = 实体的 entity id（同时被当击败 flag 写回，`SetEventFlagID(X0_4, ON)` —— flag 号 == entity 号，这是这张表最硬的一条「位置绑定」证据）；`X4` = 批次 id；`X8` = BGM。**模板里没有 npc id、没有 NpcParam 行、没有模型名。**

### 2.2 调用点：27 张图，每图一条，批次是字面量

全部 `mod/event/*.js` 上 `90005875` 共 **27 个调用点、27 个文件**（`m60_45_37_00` 与 `m60_45_37_10` 是同一 Boss 的两份 arena，各一条）。原文举例：

### 2.4 否证机制①：奖励**不**跟敌人种类走

- 25 个主条目守卫的 `NpcParam` 行：`itemLotId_enemy = -1`、`itemLotId_map = -1`、`getSoul = 0`（逐行实测，例：`npc 36502100` 黄金树守卫）。
- 反向：`NpcParam` 全表 **1384 条 `itemLotId_enemy` + 62 条 `itemLotId_map`** 引用，**没有一条**指向第 1 节那 23 个授予批次。
- 随机器自己的设计注记也承认这件事：`investigation/apply/enemy_randomizer.py:68` —— 「**itemLotId_enemy/getSoul 不在这里 —— 掉落/卢恩跟被换的敌人走是设计使然（N6）**」。也就是说：**如果**奖励挂在敌人行上，换人一定会换掉；而实测它没挂。

### 2.5 血条名同样不是身份绑定

`90005876 "Custom Boss Start Event"`（`common_func.emevd.dcx.js:7843-7869`，血条指令在 `:7861`）：`DisplayBossHealthBar(Enabled, X0_4, 0, X8_4)` —— `X8` 是地图脚本传进来的 **nameId 字面量**（`904810650` 等），即血条名写死在地图事件里，不看 npc 行。同一件事的另一面：换人后血条名不会跟着变（4.3）。

### 2.6 一句话判决

奖励链 = `地图脚本字面量(批次) → 90005875 → WaitFor(CharacterDead(entity_id)) → AwardItemsIncludingClients(批次) → ItemLotParam_map(批次) → 物品`。链条上**唯一的「身份」是 entity id，而 entity id 是位置**；npc id / 模型 / NpcParam 行都不在链上。

## 第 4 节 换人之后的推演

每条都标性质：**[实测]** 有证据 / **[推断]** 只有机制推理 + 置信度。

1. **[实测→推断，0.9] 奖励照掉，且掉的东西不变。** 换人只改 MSB part 的 `npc_id/chara_id/model`（写入侧见 `investigation/apply/msb_write.py:433` 的 `rep["applied"]`），`entity_id` 不变（`enemy_swapper.py:774` 的 `CMP_FIELDS` 把 `entity_id` 列进「不该换的字段」）。`WaitFor(CharacterDead(1045370800))` 因此仍会触发，批次仍是字面量 `1045370300`。
2. **[实测，0.95] 不会因为「换成了没血条的敌人」而丢奖励。** `90005875` 不依赖血条（血条是另一条 `90005876`），换成无名杂兵也照给。
3. **[推断，0.85] 血条名会错配。** 名字是 `90005876` 里的字面量，换人后仍显示「黄金树守卫」，打的是别的东西。这是本方案唯一的可见副作用，属观感问题。
4. **[实测，0.9] 奖励只发一次。** 模板首行 `EndIf(EventFlag(X0_4))` + 结尾 `SetEventFlagID(X0_4, ON)` —— 击败 flag 就是 entity 号，重置后不会再发，也不会因为换人变成可重复刷。
5. **[实测+推断，0.85] 额外掉落会跟着新敌人来。** `enemy_randomizer.py:68` 明说 `itemLotId_enemy/getSoul` 不保留 —— 换人后**新敌人的**掉落表与卢恩生效。玩家会同时拿到「新敌人自己的掉落」+「守卫位的露滴残渣」，且守卫原本 `getSoul=0` 会变成新敌人的卢恩额。这是「设计使然」，不是 bug，但值得写进文档（奖励不会少，反而可能多）。
6. **[推断，0.6] 一个失败模式**：若换进来的敌人不是以 `CharacterDead` 结束（被传送走、坠出地图、被移除），`WaitFor(CharacterDead(X0))` 可能等不到 → 不发放。这与原版守卫同风险（同一模板），并非换人独有。
7. **[推断，0.85] 影之地同构**：`m61_*` 的 7 个守卫用同一模板、同一参数位（`m61_47_40_00:33` 等），只是批次换成 `30710–30770`（→ 1295）。故影之地与本体适用同一结论。
8. **[推断，0.7] MSB Item 实体没参与**：27 条授予点覆盖了全部主条目，不需要靠地上拾取物解释；但「同一 arena 是否另有 MSB Item 实体」没有逐图核查（5.5），故只给 0.7。

## 第 5 节 未验证 / 卡住的地方

1. **「虫面」（中亚坛·枯萎森林）没定位到**：`NpcName` FMG 里没有对应名（只有 `141503/141504 集物虫`）。28 个名字只落了 27 个。
2. **先祖萨满（`m31_09_00_00` / entity 31090800 / npc 33700875）找不到授予行**：该图没有任何 `90005875/90005860/90005301` 引用批次。奖励来源**未验证**（可能在 MSB Item 或别的图事件里）。
3. **腐朽化身走 `90005860` 而不是 `90005875`**：`m60_51_40_00:14` 的 `InitializeCommonEvent(0, 90005860, 1051400800, 0, 1051400800, 0, 30435, 0)`，第 7 个参数才是批次（模板 `common_func.emevd.dcx.js:7466-7497`：`WaitFor(CharacterDead(X8_4)) → AwardItemsIncludingClients(X16_4)`）。位置绑定性质一样但参数位不同，多图混用时容易看错。
4. **名称→arena 的模糊匹配未消歧**：28 个名字解出 69 个候选 (map,entity)，表里 † 的四行（黄金树化身/卡利亚魔像、黄金树哨兵/诺克斯虫骑）共用 arena，谁是哪条血条名候选**没有确定**。不影响结论（每个 arena 只有一条 `90005875`），但影响「某一行名字是否真对应那个位置」。
5. **MSB Item 实体路线未逐图核查**：没有对 27 张图的 `Item/Treasure` 实体做全量比对，因此不能声称「同一位置没有任何 MSB 拾取物」。
6. **读表器不完整（重要工具坑）**：`scan_rows`（`investigation/apply/enemy_randomizer.py:187-212`）按「连续 `{id,data,name}` 三元组段」识别行，段一断就漏行；对 `ItemLotParam_map` 会漏掉 5 位数的行（`30205/30710` 全部读不到），必须按 id 暴力定位三元组才读得到（第 6 节）。因此 2.4 的 `NpcParam` 引用统计沿用旧口径（7823 行），其**完整性为中高置信，不是实测边界**。
7. **没有启动游戏验证**（任务禁止启动游戏）。以上全部是静态证据。
