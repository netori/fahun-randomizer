## 2. 槽表：唯一 id 与总数

### 2.1 方案
```
slot_id = {table}:{row_id}:{slot_index}
map:10000770:1      # ItemLotParam_map 行 10000770 的第 1 格
enemy:70010000:1    # ItemLotParam_enemy 行 70010000
shop:100018:1       # ShopLineupParam 行 100018（每行仅 1 件）
```
行 id 在三表内唯一，slot 在行内 1–8 唯一 ⇒ 全局唯一；G 计划 CSV 的 `source_table,row_id,slot` 三列拼起来就是同一把键（`investigation/randomization-dryrun/scripts/randomizer.py` 已用这三列做定位）。

### 2.2 分布事实（决定「一行多槽」要不要拆）
- map：7,285 行 1 格、1 行 2 格、18 行 3 格、10 行 4 格、5 格/7 格/8 格各 1 行；155 行空；**67 行有重复 item id**（同一行两格同物，拆槽时不能按 item id 去重）。
- enemy：3,829 行 1 格、14 行 2 格、148 行 3 格、1 行 7 格；638 行空；290 行有重复 item id。
- shop：1,553 行全部 1 行 1 件（`setNum` 全 1，:79）。

### 2.3 与 G 的互斥
G 只覆盖职业说明书物品（682 件 / 766 格，`randomizer.py` ENGINE_VERSION 1.1），三表槽不在其中；「同一份计划、同一次写入」只需保证 CSV 里每个 `slot_id` 只出现一次（G 的格也编成同形键即可）。**互斥是实现约束，不是数据冲突。**

## 3. 位置粒度：能不能到「场景/地点」

### 3.1 lot id 自带的区域编码（解码规则）
8/9 位 → `m{前2}_{第3-4}_00_00`；10 位且以 1 开头 → `m60_{第3-4}_{第5-6}_00`；以 2 开头 → `m61_{第3-4}_{第5-6}_00`（DLC）。
- 对参考 DebugText 的 4,111 条单 lot 真值：**3,471 命中 = 84.4%**（miss 几乎全是 5/6 位事件 lot 与 <1e6 小 id）。
- 对 MSB 定位的 4,110 行反查：**4,070/4,110 = 99.03%**（不一致的 40 条是重复地图副本，如 1033470200→m60_33_47 而 MSB 在 m60_08_11_02）。
- 全表覆盖：解出且地图存在 **5,155/7,472 = 69.0%**；解出但无此图 76 行（99xxx/23xxxxxx/90xxxxxxx 占位）；不可解 2,241 行（5/6/7 位事件 lot）。

### 3.2 MSB 结构定位（真正到「地点」的那一步）
MSB 里每笔拾取是 12 字节 `[partIndex u32][0 u32][lotId u32]`，part 必须是 asset（模型名 `AEG*`）。
- 例：`10000770` 在 m10 原始字节只出现 1 次（偏移 281,080），part #1159 = `AEG099_990_9003`（Shiny Item），坐标 (-266.148, 88.304, 260.007)；`10000995` 对应 `AEG099_630_9006`（Chest）。
- 全 634 图扫描（95.4 s）：命中 **4,110 行 / 4,087 格**（5,335 个大 id 行 / 5,230 格 ⇒ 行 77.0%、格 78.2%）；3,831 行唯一地图，279 行多地图。
- 真值校验：参考 `itemslots.txt` 里能给出地图的 3,151 个 lot，MSB 反查命中 **3,149/3,151 = 99.94%**（2 条差异：30200910→m30_21 而非 m30_20；1047550900→m60_47_55_10/m60_48_54_00 多副本）。
- 命令：`python %TEMP%/gf_slot_probe14.py`（全量扫描）、`probe24.py`（对参考真值）、`probe31.py`（解码一致性）。

### 3.3 赐福锚点（「哪个赐福点旁边」）
`BonfireWarpParam` 479 行，areaNo/gridXNo/gridZNo 拼图名命中现有地图 **476/479、覆盖 282 图**，posX/Y/Z 可用（`probe15/32.py`）。
- 把槽坐标与同图赐福坐标做水平距离 + 高度差，**精确复现参考标注**：10000770「19.86 away / 16.74 height」（参考 itemslots.txt:79-80 同值）；10000420「19.25 / 32.67」；10000775「26.88 / 16.73」。
- 覆盖：3,572 个槽所在图有赐福；最近距离中位 87.7 m，<100 m 58.4%、<200 m 90.7%、<400 m 99.7%。
- **结论：赐福锚点可派生，不需要人工标注**；剩余 538 个槽所在图无赐福（多为 _99 子图/竞技场/DLC 小图）。

### 3.4 定位不了的（必须承认的缺口）
- map 大 id 中 1,225 行 / **1,143 格**在 MSB 里找不到；其中 **648 行**的 item 内容与别行完全重复（疑弃用副本）。
- map 小 id（<1e6）2,137 行 / **2,171 格**是事件奖励（含 BOSS/任务），MSB 本来就没有实体；EMEVD 里只能再补 325 行（token 命中，含误配风险）。
- 合计：**7,401 格中 4,087 格有精确地点（55.2%）**；其余只能标 `locator=unknown` 或 `event`。

定位漏斗（map 表）：

| 口径 | 行 | 格 | 说明 |
|---|---|---|---|
| 全表 | 7,472 | 7,401 | 讨论稿口径 |
| id 能解出地图 | 5,155 | — | 69.0%，只能到图，不能到点 |
| MSB 精确到坐标 | 4,110 | 4,087 | 55.2% 的格；真值 99.94% |
| + EMEVD token 补充 | 4,435 | — | 59.3% 的行（含误配，需人工抽检） |
| 仅事件（小 id） | 2,137 | 2,171 | 无实体，只能标「事件奖励」 |
| 大 id 但未命中 | 1,225 | 1,143 | 其中 648 行内容重复，疑弃用 |

### 3.5 `lot_reward_index.json` 是什么
不是位置数据。由 `investigation/randomization-catalog/scripts/scan_rewards.py` 生成（输出注释见该文件 :4），结构 `{lots: 11,311 条（table/lot_id/row_name/getItemFlagId/slots[...]）, shops: 1,554, ...}`，用途是**审计时按「表/行/slot」核对 item_id 与 category**（`randomization-catalog-review/scripts/audit_candidates.py:30`、`audit_cells_vs_file.py:5`）。它可以直接当槽表的「行内格」校验器，但**不含地图/坐标/区域**。

## 5. 区域图：参考有什么、法魂能补什么

### 5.1 参考形状（annotations.txt Areas，L900–3167）
- **362 个区域**、361 条 `Req`、361 条 `Maps`；字段：`Name/Text/FullText/Req/KeyBase/MainMaps/Maps/Tags/Comment`（KeyBase 188、MainMaps 13、Comment 25）。
- Maps 去重 **484 个图名**，本 mod 实有 **462** 个（22 个不存在）；本 mod 另有 **172 张图**不在任何区域（多半是 `_99` 子图与竞技场）。
- Req 形态：**AND 为主**，只有 10 条含 OR、9 条含括号、0 条 NOT，最长 17 项；例 `annotations.txt:1008` `(stormveil_godrick AND godrick) OR (liurnia AND noliurniagate)`、`:1260` 三层嵌套。
- **56 个区域被物品/flag 门控**，66 个外部符号、77 次引用（`runegodrick`、`noliurniagate`、`rustykey`、`morgott`、`purebloodknightsmedal`…）⇒它不是纯区域图，而是「区域可达 × 关键道具布尔条件」。
- 图上有 **2 个环**（5 节点 + 2 节点，共 7 区域，如 `liurnia↔stormveil_throne`、`sewer↔sewer_flame`）；压缩后 DAG 深 **29 层**（最深 `erdtree`）。
- 一图多区域 **221 张**：263 图属 1 个区域、143 图属 2 个、39 图属 3 个、23 图属 4 个，最多 10 个（m11_00 Leyndell、m12_02 Siofra/Nokron、m13_00 Farum Azula 这类多层图）。
- `submaps.txt` 用 Y/X/Z 阈值把 73 张图切成 215 个子区域（`submaps.txt:3-16`：m12_01 的 YBelow -285=Lake of Rot、-265=Ainsel），只覆盖 221 张多区域图中的 71 张。
- 标签：`dlc` 80 区域 / 139 图；`minidungeon` 74、`catacomb` 25、`cave` 22、`grave` 10、`tunnel` 9、`gaol` 5、`forge` 3（区域级标签，不是槽级）。

### 5.2 三条不能抄
1. **Req 是人工游戏逻辑**，不是从数据推出来的（是否「需要钥匙/大卢恩/某 BOSS 已杀」由作者判定）。
2. **submaps 阈值是人工调参**（YBelow -285 这种整数），能抄形状（按 Y 切），不能抄数值。
3. **4,379 槽 / 95 标签是人工标注**（`itemslots.txt` 每槽 Text/Area/FullArea/Tags）；已知不可抄，只可当真值校验（本文的三处 99.94%/84.4%/距离复现都是这么用的）。

### 5.3 法魂侧能提供什么
- **MSB**：634 个 .msb.dcx；part 类型（m10：MapPiece 343、Enemy 283、Asset 8,016…）、模型名、坐标、entity id——**只有几何与实体，没有连通关系**。
- **EMEVD**：268 个 .dcx / 267 个 .js（common 690,670 B、m10 92,058 B，合计 5.2 MB 文本）；只有 29 个 .js 提 ItemLot，`AwardItemLot(` 仅 53 个不同参数 ⇒ 事件脚本不是物品放置的主通道，更不是连通图。
- **Param**：NpcParam（`itemLotId_enemy` 9 位 4,902 行）、BonfireWarpParam（479）、ItemLotParam、ShopLineupParam——没有「门/钥匙/电梯/传送」表。
- 本仓工具：`msb_read.py`（只解析 Enemy part，不读 EVENT_PARAM_ST）、`enemy_map_atlas.py`（634 图→map_enemies.csv/boss_rows.csv）、`enemy_emevd.py`（.js 找血条/BGM）——**没有任何区域连通/可达性工具**。

### 5.4 三级结论
| 级别 | 内容 | 数据够不够 | 估人天 |
|---|---|---|---|
| **L0** | 只给槽打标签：地图名、地图前缀类型、DLC、有限/无限 | 够（本文 §3/§4） | 2–3 |
| **L1** | L0 + 赐福锚点 + 区域名（按 Maps 映射）+ 人工校准的多区域表 + 定位置信度（located/event/unknown） | 够；多区域 221 张需人工/阈值校准 | **6–8.5** |
| **L2** | 区域图 + 区域间 Req 布尔式 + 关键道具可达性 | **不够**：需从 EMEVD/几何重建门与传送、再人工校准 362 区域 | 15–30（不确定） |

**本期建议：做 L1，L2 单独立项。** 理由：用户已定「关键道具默认冻结」；没有 Req 也不影响物品池、Bias 与重要位置面板（面板要的是 area/grace 标签，L1 就有）；而 L2 的成本主要花在不可验证的人工逻辑上。

## 9. 判词

**槽表能做，而且比预期干净**：唯一 id 是三列拼接，MSB 的 12 字节结构把 4,087 个格子钉到地图+坐标，赐福距离能精确复现参考标注（19.86/16.74 这种小数都对得上），说明「地点槽表」不是抄来的，是法魂自己的数据能推出来的。

**区域图不能做，也不该在本期做**：参考的 362 区域/361 条 Req 是人工游戏逻辑（56 个区域被钥匙/大卢恩门控，还有 2 个环），法魂侧没有任何连通数据；把它硬搬过来只会得到一张看似完整、实际不可验证的图。用户已定关键道具冻结，Req 对本期物品池没有增量价值。

**因此：本期停在 L1**——槽表 + 区域标签 + 赐福锚点 + 类型/有限/DLC/箱庭属性，把 `locator` 的不确定性如实写进 CSV；L2（可达性）等关键道具链立项时再做，先补「事件奖励→地图」这块最缺的砖。
