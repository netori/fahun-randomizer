# 敌人随机 M0：位置主表与四层分类

生成日期：2026-10-20（M0 收尾完成）　｜　对应阶段：v1 实施计划 M0（数据作业）
产物：`investigation/apply/enemy_data_build.py` ＋ `investigation/enemy_places.csv`（27,780 行 × 21 列）＋ `investigation/enemy_model_names.csv`（462 模型）＋ `investigation/apply/data/enemy_classes_v3.yaml`。`--check` 当前 **PASS（0 项不通过）**。

## 0. 三句话

1. 敌人位置的权威主键不是 csv 里那列 entity_id，而是 **(map, part_name, occurrence)**：全仓库 27,780 个敌人 part 里只有 31%（8,609 个）有实体 ID，剩下 19,171 个的实体 ID 就是 0。
2. 参考实现 enemy.txt 里的 `ID` 字段**不是** MSB 的实体 ID，所以「按 ID 对齐」这条路本来就堵死；按 part 名对齐后覆盖 77.2%，再加模型级回退到 **98.2%**，只剩 66 个模型 / 506 个位置在参考表里查不到 —— 这些已按规则全部定类（无名杂兵给统一名进 `Mob`，假人/危害物进 `Dummy` 且 keep）。
3. 没有实体 ID 的 part **仍然能换**（换人是改 MSB 的 npc/think/chara/model 字段）；数值对齐也不依赖实体 ID —— 照参考实现的做法，给每个位置克隆一条 NpcParam 行。所以 v1 的池子不排除它们。

> 补一条（2026-10-20 收尾）：同一处物理位置在磁盘上可能有**两份 MSB**（同一地点的「打开 / 封印」两态各存一份文件，例如 `m61_44_45_00` 与 `m61_44_45_10`）。本次已在表里用 `link` 列把这种成对的行串起来：**2,124 组 / 4,248 行**，所以 27,780 行实际只对应 **25,656 个物理位置**。计划层必须「同一 link 组一起换」，否则玩家从不同入口进同一地点会看到两只不同的敌人。

## 1. 为什么主键换了（证据）

| 观察 | 数字 |
|---|---|
| MSB 里 type==2 的敌人 part 总数 | 27,780（634 个 msb.dcx，**519 张图**有敌人） |
| 其中 entity_id != 0 | 8,609（31.0%） |
| entity_id == 0 | 19,171（69.0%）—— 旧 `map_enemies.csv` 把这些行也写进表，做成主键就撞成一堆 0 |
| (map, entity_id) 去重后 | 8,402 组，其中 93 组重复 |
| (map, part_name) 重复 | 28 组 → 加 occurrence 后缀，写作 `c3400_9000#1` |

> 图数口径：我们自己扫出 **519 张图**；参考 enemy.txt 只覆盖 483 张（差的是法魂新增图）。yaml 的 `assertions.distinct_maps` 已按 519 校准。

关键反证（2026-10-20 实测）：参考实现说 m12_02_00_00 的 part `c0100_9030` 的 ID 是 **2800323**，但把 2800323 当 u32 在整个 MSB（15,573,744 字节）里搜索 **0 次命中**；而同一张图里 `c0100_9024` 的 ID **12020304** 确实能在 part 起始 +0x260 找到 1 次（正好是 msb_read 读实体块的位置）。在 mod/event/*.js 里 grep 2800323 同样 0 命中。
→ 结论：参考数据里那些「无实体 ID 的 part」的 ID 来自它自己的另一套编号，**不能当 join key**；只有 part 名（enemy.txt 的 `Name` 字段，形如 `c0100_9030`）是两套数据共有的。

## 3. 四层分类的落地（cls / silo / tier / policy）

表里每行现在有 21 列，其中分类相关的八列：

| 列 | 含义 | 取值 |

**Boss 血条位置（`bar` 列）**：扫全量 267 个 `mod/event/*.js`（两种来源：地图事件直接调 `DisplayBossHealthBar(Enabled, 实体, 槽, 名字)`；以及 90005870 野外 Boss / 90005876 传送门模板的 `Initialize(Common)Event` 实体参数），命中 **246 个 (map, entity)** → 落到 **229 个位置行**（176 行 randomize / 53 行 keep），合并成 **170 个替换单元**。类分布：Boss 68 / MinorBoss 66 / Basic 32 / Miniboss 21 / Helper 20 / NightMiniboss 11 / DragonMiniboss 7 / None 4。

为什么需要这一列：血条属于**位置的 EMEVD**，不属于模型 —— NpcParam 的 315 个字段里没有任何「显示血条」开关。所以换人不会弄丢血条，但**把有血条的位置换成普通杂兵**（Basic 那 32 行就是）等于把一场 Boss 战变成路人：实测症状正是「原本有大血条的地方，随成了普通小兵」。yaml 的 `bossbar_position` 规则据此强制这些位置只换入 boss 级（见 [敌人随机_M1_计划层报告.md](敌人随机_M1_计划层报告.md) §2）。`--check` 会与磁盘 EMEVD 现算结果逐行比对，漂移即 FAIL。

## 7. 产物与用法

```
cd investigation/apply
python enemy_data_build.py --build     # 重扫 634 张 MSB（约 12s）→ 位置表 + 模型名字表
python enemy_data_build.py --check     # 严格校验（当前 PASS）：磁盘↔表↔yaml↔名字表 四处自洽
python enemy_data_build.py --stats     # 只打统计（不写盘）
python enemy_data_build.py --ref <path>  # 指定参考 enemy.txt 的路径
python enemy_data_build.py --yaml <path> # 指定分类配置（默认 data/enemy_classes_v3.yaml）
```

`--check` 校验的九组事（任一不过即 FAIL）：
1. 磁盘上的 part 与表完全一致（无缺失/无陈旧/无字段漂移）；
1b. `bar` 列与磁盘 EMEVD 现算结果逐行一致（267 个 event js，两种血条来源）；
2. yaml 里的断言数字（27,780 个位置 / 519 张图 / 2,124 组重复 MSB / 25,656 个物理位置）；
3. 每行 cls/cls_src 非空、没有 unknown、policy 合法、silo ⇔ randomize 一致、randomize 必有 tier、area ∈ base/dlc；
4. 池成员在位置表里恰好命中 1 行且 npc/model 与 yaml 一致，`unresolved` 必须仍然找不到；
4b. 多阶段组：组内每个阶段都必须在表里且全部 `policy=keep`；
4c. 重复 MSB：2,124 组 / 4,248 行、25,656 个物理位置与 yaml 断言一致；每组恰好 2 行、跨 2 张图、link 号一致、两行政策相同；带了 link 却找不到同伴即 FAIL；
5. keep_maps / keep_npc_ids / never_touch_npc_ids 与 randomize 互斥；
6. 模型名字表与位置表的模型集合、类、政策、位置数一致；
7. 最后打印 policy / silo / tier / pools / keep 原因的分布，供人核对。

文件：
- `investigation/enemy_places.csv` —— 27,780 行 × 20 列：map, part_name, occurrence, entity_id, npc_id, think_id, chara_id, model, x, y, z, cls, cls_src, area, silo, tier, policy, pools, note, **link**, **bar**
- `investigation/enemy_model_names.csv` —— 462 行：model, display_name, name_src, cls, cls_src, placements, npc_rows, hp_min, hp_max, boss_any, policy, note
- `investigation/apply/data/enemy_classes_v3.yaml` —— L1 类 / L2 silo / L3 tier / L4 policy / **14 组多阶段** / 四个池（全 ready）/ overrides / assertions

这三份已加进 `build_exe.py` 的 `DATA`（随 exe 一起打包、首运行释放）；`enemy_data_build.py` 本身是**离线数据工具**，不进 `PIPELINE`、也不进 `randgui.py` 的 `_need`。
