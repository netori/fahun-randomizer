## 0. 三句话

1. 分类的**第一消费者是界面**（玩家要能勾"这次随哪些"），引擎只消费第二层。
2. **池只决定"哪些位置参与随机"**，不再决定"谁能换谁"——能不能换由 silo（Class × 本体/DLC）、可放置性规则、政策表三件东西管。
3. 难度靠**换完之后的缩放**解决，不靠缩小候选池。

## 1. 分类的四层（已定：四层，只有第二层被引擎消费）

| 层 | 内容 | 谁消费 | 说明 |
|---|---|---|---|
| L1 **Kind / Class** | 照参考实现的 `EnemyClass`，数据只用 14 个值 | 界面（显示与分组）、silo 的键 | 不新建类；法魂特有那几类做成池（见 §3） |
| L2 **互换子池 silo** | `(EnemyClass × 本体/DLC)` ≈ 20 个桶 | **引擎唯一消费的一层** | 见 §2 |
| L3 **强度档 tier** | 复合分位切 4 档（见 §5） | 缩放、界面提示 | 只影响数值贴合，不影响"能不能换" |
| L4 **政策 policy** | `randomizable / keep / source_only / hazard / story` | 引擎（能不能动这个位置）、界面（灰掉并给理由） | 见 §4，唯一裁决处 |

数据里实际出现的 14 个类值（`enemy.txt` Enemies 块实测）：Basic 12,399 / Wildlife 7,919 / None 1,827 / Helper 410 / Scarab 201 / DupeOnly 135 / MinorBoss 79 / HostileNPC 54 / Boss 52 / Miniboss 41 / NightMiniboss 21 / DragonMiniboss 15 / CaravanTroll 10 / Evergaol 10。

**v1 在参考的 14 个值之外多两个（只影响显示与 silo 的键，不新增机制）**：

- `Mob` —— 参考表里没有、游戏也没给名字的模型（**22 个模型 / 329 个位置**；另有 2 个同样没名字、但参考表里有类，按参考类走）。命名照参考实现的兜底写法（`GameData.cs:742` 名字表查不到就返回模型号；`EnemyPreset.cs:1024` 的 `"Basic {model}"`），显示为「法魂杂兵（cXXXX）」；silo = `Mob × 本体/DLC`，**只在彼此之间互换**，不跟士兵/野兽/Boss 混。
- `Dummy` —— 假人 / 危害物：圆桌厅堂训练假人 8 个（`c8003`-`c8009`、`c8099`，hp 都是 1939 且全在 `m11_10_00_00`）、弹丸假人 `c120`、疑似 Lightning Ball 变体 `c2105`/`c2151`；一律 `policy=keep`。
- 另有 **29 个「法魂新增但有血条名」的模型**临时记 `Boss`（`cls_src=auto:bossbar`）—— 有血条名说明游戏把它们当 Boss；最终归属（楔石 / 追忆 / 圣龛 / 传送门）等 §3 的法魂池划分拍板。

完整名字表（462 个模型：291 ModelName + 136 血条名 + 24 统一名 + 11 人工指定）见 [敌人随机_模型名字表.md](敌人随机_模型名字表.md)，数据在 `investigation/enemy_model_names.csv`。

**为什么照抄这 6 个 boss 类而不自己定"主要/次要"**：参考实现的分法按机制不按重要性——`Boss`（靠 EndConds 保证可击杀）、`MinorBoss`（**按 Boss 装配**：有 segments、有血条）、`Miniboss`（具名、应当可击杀）、`NightMiniboss`、`DragonMiniboss`、`Evergaol`（监牢）。真正跑逻辑的是两个派生布尔（`ER:1007-1010`）：

- `IsBossTarget` = `Boss | MinorBoss | Evergaol`（内圈）
- `IsImportantTarget` = 内圈 + `Miniboss | DragonMiniboss | NightMiniboss`（外圈）

→ **类名给玩家看，行为看布尔**。所以 L1 只做显示，不参与"能不能换"的判定。

## 2. 池与 silo（已定：silo = Class × 本体/DLC；池名不限制候选）

- 参考实现的 silo 键是三元组 `(EnemyClass, AreaSiloType, AreaIndex)`（`EnemyPermutation.cs` 的 `EnemySiloType`，`EnemyRandomizer.cs:1528`），而 `AreaSiloType` 只有 `None | DLC | Region` 三个值（`Item/LocationData.cs:150-156`），**敌人侧只会用到 None / DLC 两档**——`Region` 只出现在物品侧，且物品侧也会被强制改回 None（`Item/ItemPreset.cs:482-484`，注释 "In development"）。
- 预设可以按类覆盖（`ClassSilo`，`ER:1530-1533`）；`overallSilo` 来自选项 `dlcsilo` 或预设（`ER:510-514`）。
- 白名单是 `randomizedTypes`（`ER:300-323`），不在里面的类**完全跳过**。

**已定：池（楔石/追忆/圣龛/传送门）不是 silo。** 池只回答"这些位置要不要参与随机"，以及"界面上给玩家哪一行勾选框"；候选集由 silo + 可放置性 + 政策决定。用户原话：「掉落物只绑定地点，不跟 boss，也就是说就算这个 boss 的位置换了其他 boss，这个其他 boss 还是掉原 boss 的东西」。

**推论（实现时要照做）**：换人时**不迁移 itemLot**、不把"原 boss 的掉落"搬到新 boss 身上，也不反过来清掉；位置上的奖励由原机制（事件/道具）负责。

**传送门的三条硬条件**（违反任一条 → 传送门永久锁死、奖励永久丢失，全库没有备用解锁路径）：

1. 只换 `npc_id`（外形/AI/数值），**保留实体本身与实体 ID**；
2. 换进来的必须是**敌对 + 会出现 + 能被杀死**（换成商人/友好 NPC/`immortal` → 这个位置再也不会死）；
3. **传送门本体 NPC `506010050` 必须显式排除**（当前代码 grep 不到，要补）；`526100965`（希芙拉河诺克隆广场的**拟态泪**）已在 `SPECIAL_BOSS_EXCLUDE` 里，保持。

证据（法魂自带可读事件脚本 `mod/event/common_func.emevd.dcx.js`，我逐行核过）：

- `$Event(90005875)`（`:7826-7840`）＝"Custom Boss Death Event"：`WaitFor(CharacterDead(X0_4))` → `AwardItemsIncludingClients(X4_4)` → `SetEventFlagID(X0_4, ON)`。**发奖与死亡旗标都以实体为主键。**
- `$Event(9005995)`（`:9047-9057`）＝"Erdtree Warps - Enemy, Obj, Guardian"：`if (!EventFlag(X8_4)) { DisableCharacter(X0_4); ... }`，**开锁只看 flag（= 守门实体 ID）**。
- 28 个守门行的 `itemLotId_map` / `itemLotId_enemy` 全为 `-1`，奖励 lot 硬编码在调用点 → 奖励**不随敌人种类走**。

**已定：传送门池默认开。** 奖励链已证不含 npc（见上），但仍有三件事必须自检，任一项不过即整体回滚：

1. 30 个开锁实体都在、`npc_id` 确实变了；
2. 换入的是**敌对 + 会出现 + 可击杀**（守卫"不会死" = 传送门永久锁死）；
3. 27 条奖励调用点仍指向原实体、原批次（`AwardItemsIncludingClients` 的第二参数不被任何写入碰到）。

**已知观感缺陷（v1 接受，v1.2 修）**：血条名由 `90005876` 按**字面量 nameId** 给，换人后血条上会是**原 Boss 的名字**。这不是坏掉，但玩家看得出来；结果表要列出这些位置。

## 4. 政策表 policy（已定：单一权威，tag 降级为显示）

一行一个 place（`map + entity_id`），只允许五个值之一：

| 值 | 含义 | 例子 |
|---|---|---|
| `randomizable` | 可以当目标被换，也可以当源 | 普通敌人、Boss、法魂四个池 |
| `keep` | 位置保持原样（不换），但可以作为**源**被换到别人身上 | 部分多阶段 Boss 的基实体 |
| `source_only` | 只能当源，不能被换进来 | 拟态泪、部分 helper |
| `hazard` | 危害物：只当源、绝不当目标 | 闪电球/鹰/猫头鹰（参考实现的 `Groups: unkillable`） |
| `story` | 任务/剧情相关，不动，也不当源 | 商人、指头女巫、传送门本体 |

每行还带：`reason`（一句话人话）、`source`（谁定的：参考实现 / 作者确认 / 实测 / 我们）、`evidence`（文件:行号 / flag / 日期）。**代码只读 policy**，不再读 tag、不再读散落的 `if`。tag 只作为派生显示。

（上次的病根：同一个"不能动"有五种写法——tag、`ref_class=None`、CSV 的 `unkillable=1`、`type_rule` 散文、代码硬编码，所以"到底几个不能动"有 9 和 174 两个答案。）

## 5. 强度与平衡（tier 已定；基准已定；实现方式 2026-10-20 修正）

**tier（已定）**：按 `NpcParam` 的 `hp` / `get_soul` / `threatLv` 算**复合分位**，切 4 档；把计算输入一起存进表里，可重算；人工只允许覆盖并记 `reason`。

**要收回的一处旧权力**：现在 `enemy_randomizer.py:665-670` 用 `ref_class` 覆盖档位——不接 ref 时 `boss 345 / elite 614`，接上后 `boss 618 / elite 449`（`Basic` 模型即使 hp 过 864 也被压回 normal）。新设计里**人工标注（`ref_class`）只能加政策，不能再改档位**。

**平衡机制（方向已定：换完缩放，不缩池）**：参考实现有 20 级缩放（ER），做法是给**每个位置**造一个 SpEffect 行（装系数）+ 一条 EMEVD 事件（`scale` / `scale2`）挂到该实体上。

**技术约束（必须遵守）**：不能改**共享**的 `NpcParam` 行来做缩放——那是按"敌人种类"共享的行，改了会全图同类一起变强。

**2026-10-20 修正（实测后改的做法，比 SpEffect 更准）**：M2 本来就要为**每个位置**复制一条 NpcParam 新行（换入者的行，npc id 往后第一个空位），那条新行是**这个位置独有**的，不是共享行。所以 `hp` 与 `掉落魂` 直接在新行上写**位置原值**即可 —— 不需要乘任何系数、不需要 clamp、也不会影响同类在别处的强度。实测这条把「换完的实际血量」误差从 31% 位置偏离 2 倍以上（最坏 68 倍）变成 0（逐单元断言）。
- 于是**系数只作记录**（`coef_hp` = 换入者原值 ÷ 位置值），不再参与写盘；`0.6×–2.5×` 的 clamp 只留给"攻击/防御/韧性"这类**没有独立行字段**、必须靠 SpEffect 乘的量（M4）。
- 代价：换入者自己的防御/韧性/攻击仍在（跟着它原本的种类走），所以"同血量但更硬的 Boss"会比原位置的怪耐打；这部分要么 M4 用 SpEffect 补，要么接受（试玩后再定）。

**已定：缩放基准 = ①「这个位置原本那只敌人有多强，换来的就调到多强」**（用户 2026-10-20 拍板）。理由：玩家在哪片地方面对多强的敌人，与"这次换成了谁"无关；跨池替换（F3）也因此自然成立。

- 缩放量：`hp / 掉落魂`（M2 直接写克隆行，精确）；`攻击 / 防御 / 韧性(poise)`（M4 走 SpEffect，clamp 0.6×–2.5×，被 clamp 的写进报告）。**不碰** AI、动作、抗性、体型。
- `hp` / 魂的系数 = 位置原值 ÷ 换入者原值（只记录，不写盘）；攻击/防御/韧性才真正乘系数。
- 普通位置同理：按该位置原本那只怪的数值对齐，不是只对 Boss 生效。

## 7. 数据形状与校验（已定：CSV/YAML 手写 + 构建时生成校验过的 JSON）

- 权威源：手写的分类表（place 级主键 `map + entity_id`），构建时生成运行期 JSON。
- 校验（**真的会红**，不像参考实现的 `Count` 只写着好看——它的 `Count` 无人校验，唯一比对在 `debugNames` 分支而那个开关默认关，`EP:966` vs `EP:1103-1122`）：
  - 每个 place 必须能解到 `npc_id`／模型；解不到就报错并列出；
  - 每类的 `Count` 与实际行数比；`policy` 与 `randomizable` 的互斥性；
  - 池成员必须全部存在；`source_only/hazard/story` 不得出现在目标侧。
- 打包副本（`_assets/investigation/...`）与工作树漂移必须能被检出（现在是静默漂移）。

## 9. 与参考实现的边界（不照搬的四件事，详见设计拆解 §15）

1. 它每次从 `Vanilla/regulation.bin` 全量重写——我们走方案层（YAFSML），不适合；
2. 它没有原子性（写一半崩＝半成品）——我们要临时目录 + 成功后整体替换；
3. 它的 `Categories` / `Count` 是给人看的死数据——我们要让校验真的会红；
4. 它没有 tier 概念——平衡是我们自己加的。
