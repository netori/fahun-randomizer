## 0. 三句话摘要

1. 旧实现不是「某处写错」，而是**六个结构性问题叠加**：层路径写错导致方案层从未生效 + 直写 MOD 本体 + 同一份 plan 被两个层各自置换 + 池子判据读错 + 按行 keep 没接线 + 提前 skip。四条用户症状（敌人没随机 / Boss 变弱智 / 外观变了数值没变 / 打不死或打不到）都是这六条的派生。
2. 真正值钱的是**写入面**：MSB 等长改写、DCX 压缩、YAFSML 方案层、EMEVD 血条名——这些已经逐字节验证过，可以直接复用。真正乱的是**决策层**：池子从哪来、谁决定身份、什么时候降级。
3. 重制第一原则：**一个敌人实例的身份只由一处决定**（MSB 里的 4 个 ID + 模型名），regulation 侧只做「跟着身份走」的数值搬运，不再并行置换。

## 1. 必须带走的地基

### 1.1 游戏数据形状（实测）

| 载体 | 事实 |
| --- | --- |
| `regulation.bin` | 2,984,544 B（现场实测 sha256 前 16 位 `7BCD46B957AC49CF`），DCX+KRAK，解包后 64.8 MB 的 BND4，**194 个 .param** |
| NpcParam | 7,823 行 × 358 B —— 敌人的数值身份（血、魂、掉落、判定体） |
| NpcThinkParam | 2,613 行 × 114 B —— AI 行为参数 |
| CharaInitParam | 3,353 行 × 69 B —— 角色初始化 |
| NpcAiActionParam | 109 行 × 10 B —— 招式动作 |
| MSB 地图 | 634 张 `MapStudio`（本体 845 个 map 文件 / 803 个 mapbnd 是另一个口径，见 §4） |

NpcParam 关键字段偏移（实测，358 B 行内）：

```
nameId            +0x00c  s32
hp                +0x024  u32
getSoul           +0x02c  u32
itemLotId_enemy   +0x030  s32   (-1 = 无掉落)
isSoulGetByBoss   +0x0b0  u8    ← 是位域里的一个 bit，不是一个整字节
npcType / teamType +0x132 / +0x133  u8
chrHitHeight      +0x154  f32
chrHitRadius      +0x158  f32
```

**NpcParam 里没有指向模型的字段**（只有 `modelDispMask0..31` / `normalChangeModelId` / `ghostModelId` / `RetargetReferenceChrId` 这类遮罩与替换位）。所以「一个实例是哪个敌人」这件事，只能在 MSB 里找答案。

### 1.2 三个写入面的能力边界

- **MSB（真正决定身份的地方）**：`PartType.Enemy = 2`（另有 `DummyEnemy = 10`）。可改四个字段：`ModelName` / `NPCParamID` / `ThinkParamID` / `CharaInitID`。
  - `int32` 等长改写；`ModelName` 只能**等长或更短**（短了尾部补 0），超长就跳过。
  - entry 内的偏移都相对 `entry` 起点；entry 之后紧跟名字串。
  - 版本头是 `"MSB "` + version `1`；DCX 外层实测 `DFLT`（zlib）游戏认（`erio` 本身只支持 KRAK/ZSTD，所以 MSB 这条要单独走）。
- **regulation.bin（NpcParam）**：改数值，**不改变身份**。改了它而 MSB 没改，等于「长得是 A、算的是 B」。
- **EMEVD**：只认 `EntityID` / `EntityGroupIDs` / `flag`，**不认** `NPCParamID` / `ThinkParamID`。所以只换 MSB 的 3 个 ID + 模型名，**不会**让血条、死亡触发、雾门失配——这是「方案乙」（只改血条名 / BGM）能做的前提，也是它的天花板：出场动画改不了，BGM 只有部分 Boss 跟得上。

### 1.3 YAFSML 方案层是唯一正确的部署面

- `Plan=` 必须写**相对 `yafsml/` 的数据根**路径：`../方案/<层名>/mod`。
  - 写「层根」= 层从未生效：19,556 行 `YAFSML.log` 里来自 `方案` 的 file override = **0 条**。
  - 写**绝对路径**会被截断在 132 字符，报 `cannot find mod Plan in directory`。
- 启动必须用 `<MOD>\启动法魂.bat`（走 YAFSML，读 ini 的 `Plan=`）；`Start_Convergence.bat` 走 me3，**不读 Plan=**，别用它验证方案层。
- `YAFSML.log` 是**追加**写，不是重写——判断某次部署先记下行号。
- 直写 `mod\regulation.bin` 是错的路线：本体与 `orig` 备份有 4,660 行 NpcParam 不同，且删掉 `Plan=` 只还原 ini、不还原本体（P0-2）。

### 1.4 已经验证过、不要重写的工程量

- `msb_write.py`：634/634 张图**逐字节零漂移**；728,264 个 part 全字段一致；与 WitchyBND 交叉 11,606 个文件只有 3 字节不同；真换两个敌人只动 4 字节。
- 跳过率从 81.76% 压到 **0.00%**（知道「该改的都能改」）。
- `enemy_emevd.py`（480 行，新写的）：EMEVD 血条名 / BGM 的写入面，方案乙就靠它。
- 物品侧管线（`erio` / `param_patch` / `native_apply` / `native_deploy` / `planlib`）是**跑通过的**，敌人侧别去改它。

## 3. 已定案的取舍（重制时照做，不用再讨论）

1. **身份唯一来源 = MSB**。外观开启时只由 MSB 决定「这是谁」；`apply_plan` 的整行置换必须跳过。只有关闭外观 / 外观失败时才走整行置换。
   > 现行代码**已经是这样**：`native_deploy.py:339-382` 在 `_visual_ok` 时只记 `{step:"enemy",mode:"visual",rows:0}`、NpcParam 一个字节不动；`plan_layer.py:370-372` 同理（降级分支才 `apply_plan(keep_model_rows=set(plan))`）。这是**已修好的状态**，重制时别把它改回「两处都置」。
2. **一层只改一处**。任何一次部署里，同一个 part 的身份只能被写一次。
3. **按行 keep 是三件事**：算出来（`manual_deploy.py` 曾算了不用）、传下去（`plan_layer.py` 曾反向不传）、验起来（`apply_plan` 的 verify 曾不转发）。三处缺一等于没做。
4. **Boss 池判据** = 有 EMEVD 血条身份的行（`boss_rows.csv`，337 条实体）；`isSoulGetByBoss` 只作线索；人形 / 通用模型名的行不进 Boss 池；仿身泪滴 `526100965` 排除。
5. **降级路径要显式**：外观层失败就整行置换，并且**在界面上说出来**；不要出现「一半换了」这种静默中间态（`native_deploy` 曾无条件写 `ok: True`）。
6. **不在游戏外替玩家拍板**：试玩 / 认可这一步只有人能说。

## 4. 需要你拍板的分歧（旧文档自相矛盾的地方）

这 6 条重制前必须先定，否则写出来的东西还是会自己打自己：

3. **覆盖率的分母是什么？** 「地图 boss 实体 1,545 覆盖 63 = 4.1%」与「51/337=15.1% → 256/337=76.0%」是两个分母（实体 vs 行）。
