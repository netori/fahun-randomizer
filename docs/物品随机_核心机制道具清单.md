- param：`EquipParamAccessory`（类别 4），`accessoryCategory=0`、`basicPrice=0`、`sellValue=1000`、`sortGroupId=90`。
- 27 个 id 每个恰好 1 条 `ShopLineupParam` 行（102800-102826，连续），`value=0`、`qty=1`、`costType=0`、`eventFlag_forStock=380000+10n`、`eventFlag_forRelease=0`；**0 map、0 enemy**。

### §4.3 货币遗物与「卡死」判断

- 灵药遗物：`20900 精华`/`20901 元素`/`20902 英勇`/`20903 振奋`/`20904 持久灵药遗物`，gt3、`maxNum=99`；地图格 16/11/10/15/9 = **61**，`getItemFlagId` 全 0。`docs/敌人随机_传送门_可换性验证.md` 已把 20900-20904 的 27 个 90005875 批次与 23 个奖励批次列过，这里不重复。
- 护符/秘宝遗物：`20950 战斗`(42 map)/`20951 传说`(19)/`20952 微光圣遗物`(7)/`20953 闪光`(7)/`20954 明亮`(8)/`20955 闪耀`(7)/`20956 魔法`(25 map + 2 shop)/`20957 守护`(31)，gt3；合计 **146 map + 2 shop**。`20956` 两条商店行 100052(3000)/100229(5000)，`eventFlag_forRelease=1034509360` 只在后者；`20975` 存在但 0 格、无名字。
- **会卡死什么**：若 8 类护符遗物中任何一类被随机掉，至少一部分目录会失去货币：秘宝要求 `20950/20951/20956/20957` 四类各 1，这四类任一丢失会让 27 颗全灭；105 护符推测对应 `20952-20955`（具体映射未验证），这四类任一丢失会让对应护符失去货币。因映射未证实，最稳是 8 类全冻；若 5 类灵药遗物中任何一类被随机掉，对应露滴失去货币。它们是**内容/构筑锁**，不是主线锁——主线锁在 §5 的钥石。
- **不会卡死什么**：105 条护符行、56 条露滴行、27 条秘宝行都是 `value=0`，按 `price>0` 池本来就不参与；只要货币在，兑换菜单仍完整。因此冻结顺序应是「先货币，后商品行」。
- **世界护符 6 个 id**：`6070 牺牲细枝`（21 map）、`3050 群聚信徒的立誓布`（1 map）、`1000 红琥珀链坠`（1600417，800）、`2130 斧护符`（1600418，1000）、`6080 勾指伪装镜`（101862，5000）、`6090 主人伪装镜`（101863，5000）。其中 3050/2130 在 105 目录里，按目录 id 冻；6070/1000/6080/6090 不在目录里，是普通掉落，**不冻**（随机它们不会卡死兑换）。若用户要求「零护符随机」，再全冻类别 4：额外 +21 map +3 shop。
- **相邻核心**：追忆 `gt101` 32 个 id / 31 map + 39 条 `value=0` 兑换行（分布在 101775-101792、102700-102726，中间有空号）；大卢恩 `gt15` 6 个 id / 12 map。两者已在讨论稿的 390 内；本票不重复计，但规格票要知道它们不是 gt1 自动覆盖的。

### §5.2 事件：全 5 块、每块消耗 1、顺序无关

- `common.emevd.dcx.js:79-83`：`InitializeEvent(0..4, 9005998, 1052520354..1052520358, 1052521354..1052521358, 8060..8064, 900000003..900000007)` —— 每块钥石一个旗标、一个可视资源、一个 goods id。
- `common.emevd.dcx.js:11439-11462`（`9005998`）：`WaitFor(EventFlag(X0_4))` → `RemoveItemFromPlayer(ItemType.Goods, X8_4, 1)` → `EnableAsset`。**旗标一开就消耗 1 块**，并点亮一个符文。
- `common.emevd.dcx.js:11464-11544`（`9006000`，Forge Teleporter）：`GotoIf(L0, AllBatchEventFlags(1052520354, 1052520358))`；否则等 `ActionButtonInArea(9221, 1052521350)`；`PlayerHasItem(8060)||...||PlayerHasItem(8064)` 才播「献上」动画；然后逐块 `if (!EventFlag(105252035x) && PlayerHasItem(806x)) SetEventFlagID(105252035x, ON)`；`RestartIf(!AllBatchEventFlags(...))`；全开后 `EnableHit`/`ActionButtonInArea(9110, ...)` → `WarpCharacterAndCopyFloorWithFadeout`。**没有「哪块必须先交」的分支，也没有「来源必须是某个 Boss」的检查。**
- `common.emevd.dcx.js:11546-11568`（`9006001`）：定义只按持有把 6969-6973 置 ON；但它的初始化在 `common.emevd.dcx.js:627` 被注释掉（`//InitializeEvent(0, 9006001, 0)`），当前未启用。`m60_52_52_00.emevd.dcx.js:307-331` 是传送门旁的教学弹窗（3000-3003），检查「持有或旗标」并提示缺哪块。两处都不改变「全 5 块」的结论。

因此：**5 块全部必需；每块只消耗 1；可以一次交 5 块，也可以分 5 次交；旗标持久；顺序自由。** 这是主线硬依赖：任何一块拿不到，传送门永不开启。

### §5.3 重排规则与验证

- **默认建议：硬冻结 15 格，不重排。** 收益只有 15 格，风险是主线；参考实现的「铃珠式内部重排」在这里没有对等收益。
- **可选重排（若规格坚持）**：只允许 **多重集保持的置换**：`pool = [8060]*4 + [8061]*4 + [8062]*5 + [8063] + [8064]`，`shuffle(pool)` 后按固定顺序写回 15 个 lot id。**绝不能每格独立 `choice([8060..8064])`** —— 那会把某块抽成 0 个，直接锁死主线。
- **副作用**：每块钥石的说明文字点名原 Boss；重排后说明与实际来源不符（文本在 `item_dlc02.msgbnd.dcx`，改它超出本票）。要么接受错配，要么不重排。
- **可达性**：15 格都是 map lot，但 lot→地图/Boss 的映射不在数据里（`rowname` 是 1350695 这类数字串，zhocn 全部 msgbnd 的 FMG 里搜不到）；教学触发实体 `1052521360` 在 `m60_52_52_00`（法姆亚兹拉区域）；传送门 `1052521350` 的地图未在数据里直接给出。**「每一格都在传送门前可达」不确定（缺 lot→地图/Boss 映射证据）**。最小验证：用一个全赐福存档，在碰传送门前把 15 格全部捡一遍（或至少每块各捡一块），确认 5 个旗标能全开、传送门能开；若发现某格在门后，把该格剔出重排池、保留原 id。
- 旧档 `docs/archive/敌人随机_2026-10/敌人随机_Boss分类.md:37` 说「集齐 5 块」，这是对的；同文 `:50-52` 把 id 写成 2712-2716，**数据是 8060-8064**，以本票为准。

## §8 不确定与最小验证

1. **6000 的语义**：只知 EMEVD 只置 OFF；若引擎/ESD 会在某个进度置 ON，9250 炼金秘宝就会可制作，27 颗成立；否则 26 颗。验证：用一个新档推进到首个追忆/圆桌，观察 9250 是否出现在秘宝显现菜单。
2. **lot→地图/Boss 映射**：15 个钥石 lot 的 `rowname` 是数字串，zhocn 全部 msgbnd 的 FMG 里搜不到；无法从数据证明每格都在传送门前。验证：全赐福存档逐格拾取（§5.3）。
3. **灵药遗物→露滴的对应**：5 类遗物各对应哪些露滴，数据里没有直接映射（菜单是 ESD/商店旗标驱动）；本票只证明「货币是遗物、商品是 56 条露滴行」。验证：每类遗物各留 1 个，逐条试兑换，记录可选列表。
4. **4 类圣遗物→105 护符的对应**：同上；`20952-20955` 是「护符遗物/圣遗物」的哪一档、对应哪些护符，未验证。冻结全部 8 类可绕开这个缺口。
5. **105 vs 103**：本票按数据 105 条（含 2 条 DLC `570xxx`）；早期笔记的 103 条是未含这 2 条的口径。若规格沿用 103，需显式补 4130/4140。
6. **`isOnlyOne` 字段**：全表读到的是 null/0（偏移可能不对），本票不用它做判据；钥石/遗物的 `maxNum` 已足够。

## §9 判词

1. **参考 8 条在法魂全部有对应，但不是「8 条都要新冻」**：5 条已在 gt1 的 390 内，真正新增的只有 `130/181`（0 格）、`250/251`（3 map）、`2070`（3 shop），合计 6 格。
2. **秘宝数据是 27 行，26 颗职业 + 1 颗炼金**；9250 的 release 6000 只在 EMEVD 里被置 OFF，这很可能就是「26」的来源，但缺引擎侧证据。冻结按 27 行全冻，成本 0 世界格。
3. **护符/灵药的真正风险不在商品行，在货币**：`20900-20904` + `20950-20957` 共 207 map + 2 shop；不冻货币，27 秘宝 + 105 护符 + 56 露滴会失去获取途径。商品行 `value=0`，按 `price>0` 池已排除，别重复计 227 行。
4. **大锅钥石是唯一主线硬锁**：5 旗标全开才开传送门，每块消耗 1，顺序无关；15 格只能做 5/4/4/1/1 多重集保持的重排，不能独立随机。默认建议硬冻结；要重排就先做 §5.3 的存档验证。
5. **推荐冻结边界 602 map + 5 enemy + 22 shop = 629 格**（其中 406 是已定 390 + 商店 gt1，223 是本票新增）；钥石可选重排则 587 硬冻 + 15 约束格。这个数可以直接进规格票。
6. **两个缺口必须在规格里留字**：追忆/大卢恩虽已在 390，但不是 gt1 自动覆盖，规格要显式写；`6000` 与 `lot→地图` 未证实 —— 前者影响 26/27 口径，后者决定钥石能不能重排。
