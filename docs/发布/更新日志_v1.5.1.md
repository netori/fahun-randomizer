# v1.5.1 更新日志（2026-10-26）

## 一句话

v1.5.0 的「二阶段变身一起搬」在实机里有两个必崩 + 一个「二阶段永远不触发」的 bug，本版全部修掉：**事件文件的尾部区段指针没跟着指令表平移**（进图加载就崩）、**克隆的敌人 part 被追加到了 MSB 文件末尾**（进游戏 50-60 秒崩）、**「结束条件」指令把 flag 状态写成了 OFF**（事件在地图加载时就自己结束，所以看不到变身）。另外顺带修了「敌人倍增」复制体的同一处追加位置问题。

## 为什么改（原话）

> 进去之后走几步路就会崩掉（m19240）

> 在宁姆格福打梅瑟莫时会卡崩掉，还没触发二阶段就会卡崩掉（m19735）

两句是不同的崩，根因也是两个，各自靠一次对照实验定位。

## 一、根因 1：EMEVD 尾部区段指针没跟着指令表增长平移

- **症状**：进图即崩。Windows 事件日志 eldenring.exe 2.7.1.0 / 0xc0000005 / 偏移 0x1202e6，两次（23:00:15 / 23:03:54）；YAFSML 日志最后一行正是 request=event:/m60_39_43_00.emevd.dcx —— 崩在我们写过的那份事件文件上。
- **离线证据**：D 层那份文件 file 857 B / plain 3272 B，header 里 arg_repl_offset=1732 / linked_offset=1924 / strings_offset=1948，而 base_arg_offset+base_arg_size=2816 —— 尾部三个区段的指针全指进了**指令表中间**。对照 vanilla 同文件：args_end=1456=arg_repl_offset / linked=1648 / strings=1672 / file=1912 全部自洽。布局公式在 30 个 vanilla 事件文件 + 268 个 mod 事件文件上逐一验证成立：arg_repl_offset = base_arg_offset + base_arg_size、linked = arg_repl + arg_repl_count×32、strings = linked + linked_count×8、strings + strings_size = len(raw)。
- **原因**：evd_add.py 重建尾部时只按「参数区增长」平移，漏了「指令表增长」—— 新增一个事件就是加指令，指令表变长，参数区起点随之后移。
- **修法**（investigation/apply/evd_add.py）：old_tail_start = ev.arg_base + old_args_size、new_tail_start = base_arg_offset + len(args_out)，tail_shift = new - old，unknown / event_layers / arg_repl / linked / strings 五个区段一律按 tail_shift 平移（count==0 的区段指向新参数区起点，strings 只在有内容时平移）；写盘前自检三条布局等式，不成立就 raise EvdAddError，不写坏文件。

## 二、根因 2：克隆的敌人 part 被追加到了 MSB 文件末尾

- **症状**：能到标题、能进世界，但 50-60 秒左右突然崩（打不打 Boss 都一样）。签名固定 0xc0000005 / 偏移 0x3f71d3 —— 用户 13:23 / 13:24 两次、我们自己挂机 13:38 复现，共 12 次同偏移。
- **对照实验**（每层只改一处，全部用「good 档 + 真进世界」口径判定，避免以前走 --play 存档库时的假通过）：

| 实验 | 改动 | 结果 |
|---|---|---|
| V1 | 纯换（无克隆、无事件） | 存活 102 秒 |
| V4 | V1 + 三个新事件 + 多一行 NpcParam | 存活 102 秒 ⇒ 事件与 NpcParam 行都不崩 |
| V5 | V1 + **末尾克隆一段敌人 part** | **崩 57 秒 / 0x3f71d3** |
| C1 | 克隆挪到旁边 8 米（排除重叠/坐标） | 崩 48 秒 |
| C2 | 克隆一个杂兵（排除被克隆者身份） | 崩 45 秒 |
| C3 | 克隆改成唯一 part 名（排除重名） | 崩 57 秒 |
| C4a | **不新增条目**，征用现成的空壳敌人 part 改成一阶段 | 存活 102 秒 |
| C4b | 同上，但改成二阶段身份 + 新增 NpcParam 行 | 存活 102 秒 ⇒ 新实体号 / 新 NpcParam 行 / 二阶段身份本身都不崩 |
| C5 | 末尾追加一条「非敌人 + entity=0」的空壳 part | 存活 102 秒 ⇒ 单纯追加条目、文件变大不崩（因为它不会被实例化） |
| C6 | 克隆同一段敌人 part，但**插进敌人分组末尾**（最后一条 type==2 之后） | **存活 102 秒** |
| C7 | C6 + 名字改成排序最前的 c0000_9009 | 存活 102 秒 ⇒ 名字排序不是约束 |
| C8 | C6 + 同族唯一名 c3251_9001（实现形态） | 存活 102 秒 |

- **原因**：MSB 的 PARTS 块里 part **按 type 分组排序**（敌人 type=2 → 4 → 13 asset…），引擎按分组遍历。把一个新的敌人 part 追在文件最后（asset 分组之后）会破坏这个前提；而「空壳（entity=0）」或「非敌人类型」追在末尾没事，因为它不进敌人实例化列表。
- **修法**（investigation/apply/phase_carry.py）：克隆条目 insert 到「最后一条 type==2(敌人) 之后」，写盘后重新解析复验「新条目确实落在敌人分组里」，不在就报错。
- **顺带修的同类问题**（investigation/apply/enemy_write.py）：「敌人倍增 / Onslaught」的复制体原来也是 append 到 PARTS 末尾 —— 同一类崩溃的潜伏版本，一并改成插到敌人分组末尾；读回校验（verify_map）按「插入位置之后整体后移」重算下标。

## 三、根因 3：二阶段永远不触发的指令编码错误

- **症状**：不崩的层里也看不到变身 —— 用户原话「还没触发二阶段」，实际情况是**新加的三个事件在地图加载时就自己结束了**。
- **证据**：把 vanilla 梅瑟莫变身事件（m21_01_00_00.emevd，event 21012811，31 条指令）与我们生成的 transition 事件逐条对齐字节：

| 指令 | vanilla | v1.5.0 写的 |
|---|---|---|
| (1003,2) END IF Event Flag | 00000100 <flag> = endType 0 / **desiredFlagState 1(ON)** / flagType 0 | 00000000 <flag> = **desiredFlagState 0(OFF)** |
| (4,2) IF Character HP Ratio | group=1，entity，cmp=5(<=)，ratio，0，1.0f | group=**0** |
| (4,0) IF Character Dead/Alive | group=1/2，entity，state=1，1.0f | group=**0** |
| (2004,7) 当 ClearSpEffect 用 | (2004,7) 实际是 **Create Bullet Owner**（4 字节，只有一个 entity 参数） | 指令号错、参数 8 字节 |

  desiredFlagState=0 的含义是「等这个 flag **熄灭**才结束事件」—— 而 transition / death 开头的 EndIf 用的是我们自己新分配的 flag，它一开始就是熄灭的，于是事件在地图加载的下一帧就结束，永远等不到血量阈值。vanilla 的顺序也核对过：先 EndIf(flag) → HPRatio 条件 → 状态切换 → 结尾 SetEventFlag(flag, ON)，我们的结构一致，错的只是编码。
- **修法**（phase_carry.py）：_end_if 首字写 0x00000100；HP / 死亡条件的条件组 0→1；ClearSpEffect 改用 (2004,21)（vanilla 728 处样本，8 字节 entity+effect）。SetSpEffect (2004,8)、血条 (2003,11)、动画 (2003,18)、面罩 (2004,26)、ForceDeath (2004,4)、SetFlag (2003,66)、网络更新 (2004,34)、AI replan (2004,20) 逐条与 vanilla 样本对齐后确认本来就对。
