# 法魂（The Convergence）黄金树传送门守门 Boss —— 奖励与随机化考证

> 只读取证：本文所有结论来自官方 wiki、本地法魂 V3.0.3 汉化本体（regulation.bin / MSB / 反编译 EMEVD）与 thefifthmatt 随机器数据。
> 标注约定：**[官方]** 官方 wiki 原文；**[实测]** 本机对资源文件静态解析得到；**[本地数据]** 本地随机器/索引数据；**[推断]** 由机制推出、未实测；**[未找到]** 明确没查到。

## 0. 结论（三行）

1. **奖励不是 boss 掉落、也不是传送门旁的拾取物，而是 EMEVD 事件在「守门实体死亡」时直接发进背包**：`AwardItemsIncludingClients(<lot>)`，lot 由各地图事件脚本硬编码（`common_func.emevd.dcx.js:7826-7840`、`:7466-7503`），与 NpcParam 的 itemLot 字段无关（28 个守门行 `itemLotId_map`/`itemLotId_enemy` 全为 `-1`）。**[实测]**
2. **只要「守门实体还在、能被杀死」，换掉它的 NpcParam 行（外形/AI/血量）不会影响传送门开启与奖励发放** —— 开锁只看 `EventFlag(守门实体ID)`（`common_func.emevd.dcx.js:9050-9057`），发奖只看同一实体的 `CharacterDead`。若换成「不出现 / 打不死 / 友方 / 无敌」的目标，则传送门**永久锁死且奖励拿不到**（无备用解锁路径）。**[实测机制 + 推断后果]**
3. **判定：可以随机（有条件）** —— 条件为「逐实体只换 npc_id、保留实体 ID 与实体本身、目标必须敌对且必定出现且可被击杀」；证据强度：机制部分 = 本地实测（硬），后果部分 = 无官方/社区实测记录（推断，见第 7 节）。

### 1.2 反编译 EMEVD：两个"自定义 Boss 死亡发奖"公共模板
`mod/event/common_func.emevd.dcx.js`（法魂自带 535 个事件文件，均带可读 `.js`）：

- **90005875**（`:7826-7840`，注释 `// Custom Boss Death Event`），参数 `(X0=守门实体, X4=lot id, X8=BGM 实体)`：
  ```
  EndIf(EventFlag(X0_4));
  WaitFor(CharacterHPValue(X0_4) <= 0);  WaitFixedTimeSeconds(4);
  ... SetBossBGM(X8_4, Stop1/Stop2); PlaySE(X0_4, SFX, 888880000);
  WaitFor(CharacterDead(X0_4));
  HandleBossDefeatAndDisplayBanner(X0_4, EnemyFelled);
  AwardItemsIncludingClients(X4_4);          // ← 奖励在这里发
  SetSpEffect(10000, 3450);
  SetEventFlagID(X0_4, ON);                  // ← 用"守门实体 ID"当死亡旗标
  EndEvent();
  ```
- **90005860**（`:7466-7503`）是另一变体，参数 `(X0=实体, X4=附加旗标, X8=实体, X12=横幅类型, X16=lot, X20=保留)`；调用点形如
  `InitializeCommonEvent(0, 90005860, <实体>, 0, <实体>, 0, <lot>, 0)`：
  读档分支 `if (EventFlag(X0_4)) { DisableCharacter(X8_4); DisableCharacterCollision(...); ForceCharacterDeath(X8_4, false); ... AwardItemsIncludingClients(X16_4); }`（`:7470-7479`），
  死亡分支同样在 `WaitFor(CharacterDead(X8_4))` 后 `SetEventFlagID(X0_4, ON)`（`:7503`）。

→ 两个模板都以**实体**为主键：死亡旗标 = 实体 ID，发奖 lot = 调用点常量。**[实测]**

### 1.5 关键负面证据：奖励不挂在 Boss 的 NpcParam 上
- 用法魂本体 regulation.bin 只读解析 NpcParam（7823 行）：28 个守门行（33001050 / 46400050 / 526100965 / 46604150 / 41200950 / 30151000 / 38050050 / 22700065 / 46900050 / 45800030 / 48100012 / 71010004 / 36502100 / 44907275 / 39020032 / 49801010 / 31700100 / 48110042 / 46020100 / 39101200 / 51920100 / 52500200 / 50811100 / 50900390 / 51600250 / 50110100 / 58400250，外加 1044530810 段未定位行）的 `itemLotId_map` 与 `itemLotId_enemy` **全部为 -1**。**[实测]**
- 把 63 条残渣 lot + 21 条金萃 lot 与全表 NpcParam 的这两个字段求交 → **0 命中**。**[实测]**
- 传送门本体 NPC 行 **506010050**（名字 id 160110 = 黄金树传送门，hp 1939）同样 `itemLotId_map = itemLotId_enemy = -1`。**[实测]**
- 因此：**换 NpcParam 行不会"丢物品表"**，因为根本没有物品表可丢；「击杀即入包」是事件行为，地上不会有可拾取的尸体包。**[实测 + 推断：`AwardItemsIncludingClients` 语义为直接给玩家]**

## 2. 换掉守门 Boss 会怎样

### 2.1 已确定（本地实测）
- **开锁只认实体旗标**：`9005995` 开头 `if (!EventFlag(X8_4)) { DisableCharacter(X0_4); SetCharacterBackreadState(X0_4,true); WaitFor(EventFlag(X8_4)); EnableCharacter(X0_4); ... }`（`common_func.emevd.dcx.js:9050-9057`；X0=传送门 NPC 实体、X4=传送门物件、X8=守门实体）。守门实体死前，传送门 NPC 处于 Disable 状态。**[实测]**
- **奖励只认实体死亡**：模板见 1.2，lot 是调用点常量。**[实测]**
- **所以换 npc_id（模型/AI/血量）→ 传送门照开、奖励照发**；唯一前提是该实体仍能被杀死。**[实测 + 推断]**
- **读档后仍保持死亡**：`90005860` 读档分支对已开旗标的实体 `ForceCharacterDeath`（`:7470-7473`）；`90005875` 分支以 `EndIf(EventFlag(X0_4))` 直接短路（`:7827`）。**[实测]**
- **目的地分支也只看旗标**（`common_func.emevd.dcx.js:9076-9103`，以 East Limgrave / Stormhill 为例）：
  ```
  if (EventFlag(1045370800)) WarpPlayer(60,45,37,0,1045372650,60);
  else                       WarpPlayer(60,45,37,0,1045372651,60);
  ```
  目的地的守门 Boss 已死 → 落到 2650；未死 → 落到 2651（需先击杀才能用那边的传送门离开）。这正是 wiki "then an additional boss will need to be defeated to leave the other side" 的实现。**[实测]/[官方]**

### 2.2 风险（推断，未实测）
- **换到"不出现"的敌人 = 永久锁死**：夜限敌人、召唤物、EMEVD 条件生成、无该地图 navmesh 的模型，都可能让实体永不进入可击杀状态 → 死亡旗标永不置位 → 该传送门永久不可用、奖励永久拿不到，且**没有备用解锁路径**（全库未发现第二处 `SetEventFlagID(守门实体, ON)`）。**[推断]**
- **换到友方 / 无敌（hp 极低但不死 / team 同阵营）**：打不死 → 同上。**[推断]**
- **"传进去出不来"**：若玩家从 A 点传到 B 点（B 的守门 Boss 被换坏），落点 2651 在 B 的 Boss 场地内、传送门 NPC 被 Disable、按 wiki 骑乘也被禁；能否开地图传送离开**未验证**（wiki 只说"要杀掉才能走"）。**[推断 / 第 7 节]**
- **血条与横幅**：`HandleBossDefeatAndDisplayBanner(X0, EnemyFelled)` 只按实体出横幅，与目标是谁无关；血条名字来自 NpcParam 的 nameId，换行后血条会显示新敌人名字（属预期）。**[实测 + 推断]**
- **"Boss 战禁坐骑"的实现位置未找到**：`common_func.emevd.dcx.js` 内与骑乘有关的只有 `:4121/:4127 CharacterRidingMount(10000)` 两处判定，没有 disable-mount 调用；该限制应在各地图事件或 region 里，与本问题无直接关系。**[未找到]**

### 2.3 换"实体"而不是换"行"会怎样
- 若方案是删/禁用守门实体、或把 `9005995`/`90005875` 的参数槽改错（X0/X8 对不上），旗标永不置位 → 与 2.2 同款锁死。**换实体不是可选项**。**[推断，机制必然]**

## 3. 重生与唯一性

- **唯一实体**：每个守门 Boss 是各地图 MSB 里的一个 NPC 实体（如 `m60_41_37_00.msb.dcx` 的 `eid=1041370800, part=c4690_9000, npc_id=46900050`），一图一个，无第二实例。**[实测]**
- **不随赐福重置复活**：全库未找到对这些实体的"重生/复活"事件；`90005875/860` 只做"死亡→置旗标"，且读档时对已开旗标的实体强制执行死亡。**[实测 + 未找到反例]**
  注：`docs/archive/敌人随机_2026-10/敌人随机_Boss分类.md:110-111` 记录法魂有 **Boss Resurrection Altar（BOSS 复活圣坛）**可复活再打（Margit / 熔炉骑士 Siluria / 拟态泪等），但**该圣坛是否覆盖这 28 个守门 Boss、复活后是否清掉死亡旗标（从而把传送门重新锁上）未验证**。**[未找到]**
- **重复发奖**：`90005860` 的读档分支会再调一次 `AwardItemsIncludingClients(X16)`，但每批 lot 都带 `getItemFlagId`（如 530140），参数语义为"已获得则不再发"，故不会刷物品。**[推断，依据 paramdex ItemLotParam 旗标语义 + 1.4 数据]**
- **合作模式**：`AwardItemsIncludingClients` 会同时发给客户端；读档分支在非主机世界先 `EndIf(!PlayerIsInOwnWorld())`。**[实测]**

## 4. 其他随机器怎么处理这 28 个

  - 发行数据 `randomizer/diste/Base/enemy.txt`（102,916 行）：`Waygate` = 0 命中，`Physick|Golden Extract|Remnant` = 0 命中；`Erdtree` 73 条全是原版敌人定义（如 998 Erdtree Avatar、1017 Erdtree Burial Watchdog）。**[本地数据]**
  - 源码检出（`C:/Users/20905/AppData/Local/Temp/dsh_gh/sr`）：`waygate` / `convergence` 均 0 命中 → **没有任何针对传送门的规则或排除**。**[本地数据]**
  - 它确实处理"换敌人后 Boss 奖励去哪"：`sr/RandomizerCommon/Elden/EldenEnemyEditor.cs:771-850` 的 `getFlagRows` 读 `row["itemLotId_" + lotType]`，把原行的 map 型 lot 迁移到自己新建的 `ItemLotParam_map` 行并 `row["itemLotId_map"].Value = -1`（`:812-813`、`:835-847`）。
  - 但**对法魂这 28 个守门行是空操作**：这些行的两个字段本来就是 -1、奖励在 EMEVD 里，所以它的"迁移 lot"逻辑既不会丢奖励、也不会保护传送门网络。它把守门 Boss 当普通敌人随便换 → 后果完全由 2.1/2.2 的机制决定。**[本地数据 + 推断]**

## 5. 我们该怎么办（≤5 条）

1. 把 30 个守门实体做成"可换但白名单"：只改 MSB 里的 `npc_id`，实体 ID、实体本身、`9005995/90005875/90005860` 的参数槽一律不动。
2. 目标池只收"该地图必定出现、敌对、可被击杀、非夜限/非召唤/非 EMEVD 条件生成"的敌人（现有 `enemy_randomizer.py:637` 的 `team_type in hostile and hp > 0` 是必要条件，不够）。
3. 传送门本体 NPC **506010050** 必须显式排除（当前 `.py` 里 grep 0 命中，说明没有显式规则）；`SPECIAL_BOSS_EXCLUDE = {526100965}`（拟态泪）保持现状。
4. 每换一个守门点都要实测"击杀→旗标→传送门可用"，并且**至少做一次读档后复测**（贴图/血条/BGM 是否崩都要看），不做纯静态放行。
5. 没有实测覆盖之前，默认把这 30 个从池里排除 —— 失败形态是"传送门永久锁死 + 奖励丢失 + 可能困在对面"，代价不可接受。
