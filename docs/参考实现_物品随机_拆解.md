# 参考实现拆解：thefifthmatt ER Randomizer 的物品随机是怎么设计的

> 对象：thefifthmatt/SoulsRandomizers 的 Elden Ring 分支。用户手里是 v0.12.2（2026-09-09 编译产物）；本笔记以 master 源码为准（commit `97caa76`，2026-10-20，"AP release features"），数据核对了本地包 `diste/Base` 与 clone 内 `diste/Base` 两处（一致处只标一处）。
> 只回答物品侧：**覆盖哪些面、池与规则是什么形状、关键道具怎么保证拿得到、最后写哪些文件**。敌人侧见 `docs/参考实现_thefifthmatt_设计拆解.md`、`docs/参考实现_拆解/A_主流程与分类学.md`。
> 引用约定：`RandomizerCommon/…` 相对源码 clone 根；`diste/Base/…` 相对本地包 `randomizer` 根；拿不准写「不确定（缺什么证据）」。

## §0 三句话结论

1. **物品侧的随机单位不是「表里的行」，是「地点槽」**：4,379 个槽（`diste/Base/itemslots.txt`）被归成三层 silo——随机类型（有限/无限/商店/可刷）× 区域（base/DLC/region）× 物品类别，置换只在同一 silo 内进行；`ItemLotParam_map`/`_enemy`/`ShopLineupParam` 只是三种落点。
2. **关键道具另走一条图求解，不靠坐标**：363 个区域节点、362 条布尔 `Req`（`diste/Base/annotations.txt:900-3242`）先被折叠成「只以物品为变量的可达条件」（`KeyItemsPermutation.cs:1008-1101`），再对每件道具求 `!reqs[a].Needs(item)` 的可用区域集，最后按区域剩余容量落子；解不出来就换种子重试，不降级。
3. **「随机什么/随机到哪/默认值」全是数据**：默认预设就是 `annotations.txt` 的 `DefaultPreset` 段（`:4261-4554`），10 条放置规则各带一条「先命中先用」的 `ModeSwitch` 链；代码只负责解释这份数据。所以它可审阅、可覆盖、可外挂（AP 预设走同一条路）。

## §2 它到底随机哪些「面」

「面」由 `LocationData.cs:273-294` 的 `ScopeType` 定义，不由表名定义——这是全篇最值得抄的一个决定：

| ScopeType | 含义（源码注释） | 落在哪张表 | 默认随不随 |
|---|---|---|---|
| `Event` | 有事件 id 保证「只能拿一次」 | `ItemLotParam_map` / `_enemy` | 随（若是关键道具则进 §5 流程） |
| `Entity` | 靠实体 id 保证一次性（无 flag） | `ItemLotParam_map` | 随；**ER 未标注的 Entity 槽直接不随**（`Permutation.cs:111-124`） |
| `Material` | Boss 追忆武器，数量恒 1 | `ShopLineupParam` | 随（独立 silo） |
| `ShopInfinite` | 无事件 id 的无限库存 | `ShopLineupParam` | 随（无限 silo） |
| `ShopInfiniteEvent` | 先有限后无限 | `ShopLineupParam` | 随（Mixed） |
| `Model` | 无 flag、可无限刷的敌人掉落 | `ItemLotParam_enemy` | 随（无限 silo）；`enemyinf` 标签可整类关掉（`:126-129`） |
| `Special` | 正常拿不到 | — | 随（有限 silo） |
| `Asset` | 场景资源采集 | — | **不随**，只在地图里换依赖（`:145`） |

除物品格之外，物品侧还动两块：**初始装备**（`Randomizer.cs:519` 无条件跑 CharacterWriter，不读物品池）与**合成物品**（`NewItems`，如「地区版石剑钥匙」`annotations.txt:3243-3595`，写 `EquipParamGoods` 新行 + FMG，见 §8）。

## §3 数据形状：标注文件就是引擎

`diste/Base/annotations.txt`（4,663 行）分 13 段，逐段都是可读的 YAML 子集：

| 段（起始行） | 规模 | 作用 |
|---|---|---|
| `ConfigItems`（1） | **47** 个 `GroupName` | 物品的语义组 + `KeyCount`/`EndID`/点名排除 |
| `StartingGroups`（573） | 5 组 | 「非关键但重要」的起始池（卢恩/种子/飞刀/烤肉/格雷斯），带数量区间 |
| `Config`（775）/ `ConfigVars`（795） | 7 对 `Oneof` + 7 条宏 | UI 互斥对；`dlcopen_event: mohg2 AND radahn` 这类宏 |
| `Events`（803） | **46** 条 | 事件节点：`Name/Text/Req`，`Req` 只能引用区域或宏 |
| `Areas`（900） | **363** 条（362 有 `Req`，362 有 `Maps`） | 区域图：`Req` 是布尔表达式，另有 `KeyBase`/`Tags`/`Maps` |
| `NewItems`（3243） | 54 条 | 合成新道具（`Switch/BaseID/Parent/Area/Logic`） |
| `PlacementRestrictions`（3596） | **104** 条 | 「第 N 份必须落在某区域之前/之后/之内」的守恒 |
| `SpecialModes`（4239） | 6 条 | race/norandom 两套并行开关映射到物品集合 |
| `DefaultPreset`（4261） | 1 份（`Version: 2`） | 默认 NorandomItems/RemoveItems/Placements/PremiumGroups/LocationGroups |
| `ItemExcludes`（4555） | 7 条 | 由标签派生「不进池」规则 |
| `ItemPriority`（4586） | 有序组 | 掉落权重（bias）用的优先级 |

另三份数据：

- `itemslots.txt`：**4,379 行 `- Key:`**，4,379 个互不相同的槽；每槽必有 `Area`/`Tags`/`Text`/`DebugText`（`Text` 是人写的地点描述，例：`Sold by Gostoc after finishing Nepheli and Kenneth Haight's quests`，`itemslots.txt:13`）；`FullArea` 2,352 条、`QuestReqs` 140 条、`Location` 仅 67 条（说明多数槽靠 `Key` 里的复合编码定位，而不是单一人为 id）。**95 个不同标签**（`missable`/`questreward`/`minidungeon`/`boss`…）是后面所有过滤的词汇表。
- `iteminfo.txt`：`ItemNames` 2,453 条（accessory/goods/gem/protector/weapon 五类）；`ItemGroups`（`:3437`）**恰好 29 个组**——讨论稿的「29 个语义物品组」出处在此，但它是**数据侧聚合**，运行时用的组来自 `ConfigItems` 的 47 个 `GroupName`（`AnnotationData.cs:287-296`），另有代码派生的 `rare`/`legendary`/`dlc`（`:351-353`）。两个 29/47 不是一回事，别混。
- `itemevents.txt`：30 条 `ItemTalks` + 191 条 `ItemEvents`，是「某个事件在检查某件道具是否到手」的模板库（`ItemEventConfig.cs:33-91`），§8 的 flag 迁移全靠它。

## §4 三层 silo：随机发生在哪一格

`Permutation.cs:384-401`：`LocationSilo = (RandomSilo Type, AreaSilo Area, ItemSilo Item)`。

- `RandomSilo`（`:331-364`）：`Finite / Infinite / Mixed / Self / Remove / Crow / InfiniteShop / InfiniteGear / InfiniteCertain`，由 `ScopeType` 机械映射（Event/Material/Entity/Special→Finite，ShopInfinite→InfiniteShop，Model→Infinite，ShopInfiniteEvent→Mixed）。**同一 silo 内才允许互换**，所以「无限商店的东西」永远不会变成「地图上的一次性拾取」。
- `AreaSilo`（`LocationData.cs:150-156`）：`None/DLC/Region`——DLC 开关关着时，DLC 区域自成一池（`KeyItemsPermutation.cs:283-286`）。
- `ItemSilo`（`LocationData.cs:159-168`）：`None/Manual/WeaponType/ArmorType`；注释明确 **关键道具不许进 item silo**（`:185-186`），否则「剑换剑」会把钥匙换没。
- 装备另有 `gearSiloVariants`（`Permutation.cs:366-380`）：护甲一律按装备处理，武器除箭（id 50,000,000–60,000,000）外按装备处理。

## §5 关键道具与「重要地点」

**三态是 UI 的收敛，数据层是 5 值枚举**（`ItemPreset.cs:35-43`）：`Unspecified/Norandom/Anywhere/Important/Custom`；UI 三个 radio 分别落到 `Norandom`/`Anywhere`/`Important`。`Important` 的含义不是「重要物品」，是「只放在**重要地点**」——重要地点 = 槽标签满足「`racemode`+`boss`」（默认预设的 `Requires`，`annotations.txt:4297-4301`）且不命中 `missable`/`minidungeon`(nocaves)/`night`(display) 的槽（`AnnotationData.cs:608-648`）；UI 再把 `default_keyloc`/`default_boss`/`raceloc_{scadu,health,shops,altboss}` 作为可选加项叠上去（这两项 checkbox 的出厂勾选状态我没在源码里读到，不确定）。

**ModeSwitch 是这套设计的枢纽**（默认预设 `annotations.txt:4309-4314`）：

```
Mode: Important                    # 默认
ModeSwitch:
- Mode: Norandom   Switch: norandom     # 勾了「不随机」→ 不随
- Mode: Important  Switch: racemode_key # 勾了 race mode → 只放重要地点
- Mode: Anywhere                        # 兜底 → 随便放
```

先命中先用，最后一条无开关即默认。**这解释了讨论稿里那 10 条规则为什么长得像配置**：它们就是配置（`annotations.txt:4293-4485`，KeyItems/QuestItems/CoreMechanics/SacredFlaskUpgrades/UpgradeBellBearings/ShadowRealmBlessings/SecondaryMechanics/BossTools/BaseOnlyItems/DlcOnlyItems）。其中 `CoreMechanics` 收着灵马笛/灵药瓶/工匠包/招魂铃/灯笼/磨刀石——它们同时也进了 `NorandomItems`，所以「默认不随」是**两条规则叠加**的结果（`:4261-4287`）。

**求解怎么工作**（`KeyItemsPermutation.cs`）：

1. 事件与区域建节点，`Req` 先代入宏并 `Simplify()`；恒假节点进 `unusedAreas`（`:238-258`）。
2. 区域按「至少需要几件关键道具」递归累计（`:389-407`，注释承认 ER 有 `leyndell→sewer→deeproot→leyndell` 环，遇环回退）。
3. `CollapseReqs`（`:1008-1101`，注释自称 "The core routine at the center of placing key items"）把「区域条件」折成「物品条件」，于是能回答「哪些区域无条件依赖这件道具」。
4. 对每件道具：`allowedAreas = areas.Where(a => !reqs[a].Needs(item))`（`:624`），再与 `PlacementRestriction.KeyAreas`、区域 silo 求交（`:642-653`）；交集空就抛 `Nowhere to place item with extra restrictions`（`:657`）。
5. 按权重选区域（`:670`），然后把选中区域的下游权重按 `1/(scaling*spreadScaling)` 摊薄（`:709-718`），并把它的 `Counts` 减 1；减不出来抛 `Ran out of space to add …`（`:1121-1132`）。
6. 环检测失败不硬修，抛 `Unsolvable seed: hard dependency loop`（`:1028-1048`）——**换种子重试**。
7. 最终失败信息写得很直白：`Could not place all important items… Try rerolling the seed, reducing the number of important items or item restrictions, or increasing the number of important locations.`（`Permutation.cs:43-45`，`:1802` 抛出）

**没有区域标注能不能做关键道具随机**：能，但只能做「不保证可达」的那种——默认预设的兜底 `Anywhere` 本身就允许道具落在打不开的地方；要保证「钥匙在锁之前」必须同时有 `Req` 图与槽的 `Area` 归属。ER 的做法是「无标注的槽直接不随」（`Permutation.cs:111-124`），而不是猜。

## §6 它不随机什么

四层过滤，从粗到细：

1. **全局点名表** `DefaultPreset.NorandomItems`（8 条，`annotations.txt:4261-4287`）：灵马笛 `goods:130`、灵药瓶 `goods:250`、工匠包 `goods:8500`、招魂铃 `goods:8158`、磨刀石 `goods:8590`、灯笼 `goods:2070`、两个牢狱钥匙（`Switch: '!gaolkeys'`）。
2. **语义组** `norandom`（`:154-179`）：血瓶 `3:1000`/`3:1050`、地图碎片 `3:8600-8618` 与 `3:2008600-2008604`、NPC 铃珠 `3:8910-8944`、无 flag 的祝福/炖菜等；`otheritems`（`:180-186`）收灵马笛。
3. **派生排除** `ItemExcludes`（7 条，`:4555-4585`）：`missable norandom nokey end → keyitems`、`exclusive norandom missable → questitems`（含 Shabriri Grape/Seedbed Curse/Deathroot 点名）、`missable end → upgrades`、`shop → bosssouls`、`boss altboss shop → souls`…… 形状是「用标签排除标签」，不是黑名单。
4. **槽级标签**：`norandom`/`RaceModeTags`/`crow`/`partdlc` 任一命中即不随（`Permutation.cs:79-134`）。

**蛇矛（Serpent-Hunter）正好证明「排除表不是一张表」**：`README.md:209` 把它列进「默认不随机」，但 `annotations.txt` 与全部 `.cs` 里找不到这个名字；它其实是被**槽标签**挡下的——`itemslots.txt:9533-9540` 那一槽（Rykard 房间，`Area: volcano_rykard`）写着 `Tags: norandom`。所以完整答案是四层并集：**点名（`NorandomItems`）+ 语义组（`norandom`）+ 标签派生（`ItemExcludes`）+ 槽标签（`Tags: norandom`）**。要复刻这套，就得同时有这四层，缺一层就会出现「某件东西在 A 处不随、在 B 处随」的怪现象。

## §7 商店：为什么它不能只换 id

`ShopCells` 把一行商店抽象成四件事（`ItemLocEditor.cs:328-382`）：`Item = equipType+equipId`、`EventFlag = eventFlag_forStock`、`Quantity = sellQuantity`、`Value = value`。写入时（`PermutationWriter.cs:750-843`）：

- **整行拷贝**：`shopCells = 源行的 DeepCopy`，不复制就不随机（`:754-757`）——商品名、图标、库存上限随之走，不需要逐字段重建。
- **旗（解锁/库存）跟着走**：目标行原来的 `eventFlag_forStock` 先记住（`:765-766`），永久旗与临时旗之间做一次重写（`:767-793`），最终 `EventFlag = infiniteMixed ? -1 : shopEventFlag`（`:794`）——`-1` 就是「无限库存」的编码。
- **价格重新采样**，不是照抄：按 `PriceCategory`（`:85`，武器/护甲/护符/法术/箭/强化石/有限/无限 goods…）从同类价格样本里抽（`:797-811`）；`costType > 0` 的自定义商店保留目标价（`:830-833`）。
- 被并入别的槽的旧商店行**删除**（`:456`/`:540-542`）；`ShopLineupParam_Recipe` 单独遍历（`EldenItemEditor.cs:2705`）。
- `SetShop` 刻意不碰 `eventFlag_forRelease`/`mtrlId`/`costType`（`ItemLocEditor.cs:81-101`），缺 `nameMsgId`/`iconId` 时写 `-1`。

对照我方：只改 `equipId/equipType` 等于「换货不换价、不动旗」，结果是**价格与解锁状态留在目标世界**——若同档同价（讨论稿方案乙），这是最省事且自洽的；若不约束档位，就会出现「1 符文买传说武器」。参考实现用「整行拷贝 + 价格重采样 + 旗迁移」换来了自由，也换来了「价格可能不合经济」的风险，它靠 `PriceCategory` 分桶压住。

## §8 最终写哪些文件

| 类别 | 写什么 | 触发条件 |
|---|---|---|
| PARAM | `ItemLotParam_map`、`ItemLotParam_enemy`、`ShopLineupParam`（+`_Recipe`）、`EquipParamGoods`（新道具/手势替身） | 物品随机必写 |
| PARAM（少量） | `GestureParam`、`SpEffectParam`、`BonfireWarpParam`、`ObjActParam`、`AssetEnvironmentGeometryParam` | 合成道具/封印开关等功能项（`EldenItemEditor.cs:218-235` 附近） |
| MSG/FMG | 新道具的 `GoodsName/Info/Caption`（武器/护甲/护符/宝石同名三件套）、`BloodMsg:9100`、map msg `265030500` | 造新 id 或改写外部道具时；纯换 id 不写 |
| EMEVD | **item flag 模板**：把「事件里检查道具 X 是否到手」重指向新槽的 flag | `EldenItemEditor.cs:1027` 起遍历全部 `game.Emevds`，命中模板才登记 `WriteEmevds` |
| MSB | 加宝箱/封印物、复制碰撞体、改资产使能 | 仅限功能开关（`:1862`/`:2121`/`:2187`/`:2322` 四处 `game.WriteMSBs.Add`） |

**关键判断**：物品本体全在 regulation，**不改地图坐标**；改 MSB 只发生在「新增物理点位/封印」这类功能上。真正容易被忽略的是 EMEVD——一件关键道具换了位置，所有「拿到它才开门」的事件都要跟着改检查对象，否则拿到也没用。它靠 `itemevents.txt` 的 221 条模板做这件事；**这也意味着「移动有事件依赖的关键道具」比「移动普通掉落」贵一个数量级**。

## §9 对现有方案的判词

**可以抄的形状（6 条，按性价比排序）**

1. **显式地点池**：把「格」做成一份可读表（槽 id/表/行/区域/标签/是否关键），而不是散在代码里的行号。我方 11,700 格完全装得下，且这份表本身就是审查界面。
2. **语义物品组 + 三层 silo**：先分「有限/无限/商店」，再分「区域」，最后分「物品类别」；这一步能把我方「同类分层池」从建议变成机制，且天然阻止「商店货变成地图一次性拾取」。
3. **三态 + ModeSwitch 链**：关键道具的三种行为用一条「先命中先用」的规则链表达，默认值放在数据里。这比我方现在把「合理度/档位」写在代码里更容易被讨论、被回滚。
4. **不变量表**：`PlacementRestrictions` 的 `Amount/Before/UpTo/After/Inside` 与我们的「守恒」同构——它管「第 N 份不能早于/晚于某区域」，我们管「数量与价格守恒」；形状可抄，数值不可抄。
5. **默认预设是数据**：默认档位应是一份随包发布的配置文件（它甚至带 `Version: 2` 做迁移），不是代码常量。
6. **失败即报错、换种子重试**：关键道具放不下时不降级、不静默，直接把「要么换种子、要么减限制、要么加地点」三个选项写进错误信息（`Permutation.cs:43-45`）——这是可运维性。

**抄不了的东西**

- **标注资产**：4,379 槽 × 手写 `Text`、363 区域 × 362 条 `Req`、95 个标签、104 条放置限制、221 条事件模板——这是数年逆向 + 人工描述，不是算法能补的。
- **数值**：`Amount/Before` 的具体数字、价格分桶、`ItemPriority` 顺序，都是按原版 ER 的关卡与经济学调的；The Convergence 的数值/掉落比例/敌人配置都不同，照抄会立刻失真。
- **旗迁移那套**：依赖他对每个事件模板的逆向；我方若坚持「只动 regulation、不动物件旗」，就应当**明确不随机有事件依赖的关键道具**，而不是假装安全。

**对「说明书 G + 合理度/档位 + 守恒」的兼容影响**

- **G 不冲突**：把 G 看成物品池的一个子集即可；G 内的守恒规则可映射成 `Unique{Amount, …}` 形状，不需要改现有语义。
- **合理度要换机制**：参考实现的「难度」是 `BiasWeights`（`KeyItemSpread 0-20`、`ItemSpread 0-15`、`KeyItemChain 1-100`，`RandomizerOptions.cs:376-418`）+ 区域权重摊薄，不是逐件打分。可借的是「权重 + 摊薄 + 链长」三旋钮，不是它的数值。
- **商店是最大分歧点**：它换价、换旗、换库存；我方只换 id/type。若 P2 要动商店，建议先只做「同类别同价格档」的置换（不碰 `value`/`eventFlag_forStock`），把「换价」留到有经济校准之后再谈——参考实现的价格重采样是为「完全自由的池」服务的，我们没有那个自由度。

**三个待定（都需要人拍板，不是技术问题）**：关键道具是否纳入 P1（参考实现把它单列一条图求解，成本最高）；商店是否允许跨价档（决定要不要引入 `PriceCategory` 式分桶）；是否接受「有事件依赖的关键道具一律不动」（决定要不要做 EMEVD 迁移）。
