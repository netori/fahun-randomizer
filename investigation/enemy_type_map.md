## 2. 归类的证据链

名字只有三条路可走，实测命中：

| 来源 | 怎么来的 | 命中 |
|---|---|---|
| E1 血条名 | `boss_healthbar.csv` 的 (map, entity) 在 `map_enemies.csv` 查到 model；**名字是权威显示名**（NpcName FMG）| 307 条血条调用命中（23 条没查到实体）|
| E2 Boss 行名 | `boss_rows.csv` 的 model + boss_name（337 行）| 336 |
| E3 行名 | `enemy_table.csv` 里非空 `name` 的行，按 npc_id 前缀解析回 model | 30 个模型 |

**E3 的坑（重要）**：`enemy_table.csv` 7823 行里只有 736 行有名字，而且**几乎全是商人/铁匠/任务 NPC**（咖列、伊吉、修古、米利耶…）—— regulation 的 `NpcParam.nameId` 对**普通杂兵是 0**。所以 `enemy_table` 的 name 只能识别『非战斗/NPC』，识别不了杂兵。这就是 462 个模型里只有 161 个能对到名字的根本原因。

**CSV 里两列 hp**：`hp_median` 是**直接抄输入** `model_types.csv` 的（按 model 前缀聚合全部命中行）；`hp_median_mapped` 是本脚本另算的『只按 `map_enemies.csv` 里真被放置的那些行』中位数。实测两者在 **31 个模型**上不同（差一个档）—— 对齐既有口径用前者，自己复核用后者。

**另一件必须交代的事**：`npc_id -> enemy_table.row_id` 的解析规则是『模型号 + 2 位变体』（`4500` → `45000000` / `45000042`）。实测 27780 条放置里 27261 条能解析（97.0% 命中），剩下 519 条解析不出、其中大头挂在 `c0000` 上（见 §6 第 5 条）。

## 3. 为什么不用关键词自动分类（实测反例）

文档 §1 给的是**按中文名关键词**分类。本脚本第一版就是那么写的，实测误差很大：

| 模型 | 关键词会判成 | 实际（名字证据）| 为什么错 |
|---|---|---|---|
| `c3200` | 虫/花/菌（含『花』字）| 流浪商人咖列 / 拾荒商人 / 受囚商人 | 『花』字误伤 |
| `c4491` | 巨人/巨兽（含『大』字）| 小壶 | 单字规则误伤 |
| `c4470` | 骑士/重甲 | 掳人少女人偶 / 扭曲的掳人者 / 弗兰肯-掳人者-斯坦 | 同名多义 |
| `c3480` | 骑士/重甲 | “剥尸王”迪鲁 | 同名多义 |
| `c4850` | 未分类 | “塑灵者”凯玛（施法者）| 没有关键词 |
| `c2030` | 巨型Boss | “满月女王”蕾娜菈 | 规则顺序把 Boss 抢走 |

→ 所以本表改成**人工复核口径**：161 个有名字的模型逐个钉死（脚本里的 `CURATED` 表），并且每次跑都**核对名字确实存在**（对不上就打 `CURATED-MISMATCH`；本次不符 0 条）。这也正是 `docs/敌人随机_敌人分类.md` §1 自己说的：『自动分类只能做初稿 —— 最终要落成一张人工复核表』。

## 6. 最不确定的地方（如实记录）

### 6.0 先说否定结果：同族外推被实测否掉了

最初想用『model 编号邻近 = 同族』（`c4500`–`c4520` 确实全是龙）来覆盖那 301 个没名字的模型。**做了留一验证，不成立**：

| 外推方式 | 留一验证命中率 | 瞎猜基线(~6~10%) | 结论 |
|---|---|---|---|
| 按 model 编号 ±10 同族投票 | 44.4%（覆盖 27/154）| ~6~10% | 不够，删掉 |
| 按 model 编号 ±15 同族投票 | 32.1%（覆盖 28/154）| ~6~10% | 不够，删掉 |
| 按 model 编号 ±20 同族投票 | 30.0%（覆盖 30/154）| ~6~10% | 不够，删掉 |
| 按 model 编号 ±40 / ±60 | 29.4% / 18.2% | ~6~10% | 更差 |
| 按体型档（判定用的就是它）| 体型·大/巨 66.7%（12/18） / 体型·巨/龙 66.7%（14/21） | ~6~10% | 只报**体型**，不报敌型 |

> 体型档那两行报的是**粗族命中率**（判据放到最宽：判『大东西』时，只要真值落在 巨人/巨兽、龙/龙裔、Boss/领主、魔像/人造、虫/花/菌 里就算命中）。也就是说：体型能告诉你『这是个大东西』（六到七成），**不能**告诉你它是龙、是巨人、还是巨兽。

→ 所以 CSV 里 `low` 的那批：**体型档是量的，敌型是没判的**，两类分开写。

### 6.1 具体盲区

1. **无名字的 301 个模型是最大盲区**（占总数的 65.2%）。现有五个输入里**没有任何字段**能推出它们的敌型 —— 这是输入的上限，不是方法的偷懒。
2. **同一模型挂多个敌型**。实测同一模型最多挂到 3 个不同名字（`c3300` = 诺克斯修士/诺克斯剑士/诺克斯蚁骑士/黄金树看护者）。血条名是**按实体**给的，一个实体也可能有 2 个名字（相位变化/Boss 替换）：实测 255 个有名字的实体里 14 个名字数 >1。所以『这个模型叫什么』本身有时是多义的，`CURATED` 取的是**出现最靠前的那个身份**。
3. **E3 行名几乎全是 NPC**：本表把命中 E3 的模型归进『非战斗/NPC』，但**没有独立验证**『这个名字对应的实体是不是真的不参战』—— 只验证了『regulation 里给了它名字』。这一条必须人工过。
4. **骑乘/成组这一类本表没建**。血条名里跟骑乘相关的只有『“黑夜骑兵长官”西古尔』（归了骑士/重甲），`map_enemies.csv` 也没有『坐骑』列。文档说骑乘单位换掉容易出事，但**现有输入识别不出哪些是骑乘单位** —— 要么补 EMEVD/模型列，要么人工列白名单。
5. **`c0000` 是垃圾桶，不是模型**。它 417 个放置点里 **403 个的 npc_id 在 `enemy_table.csv` 里解析不出行**（`523250114` 这类），挂着 13 个完全不同的名字（帕奇/古龙人/红熊/孤牢骑士…）。进随机池前要单独处理：它大概率是**解析失败的缺省值**，不是一种敌人。
6. **`c1000` 可疑**。它 1061 个放置点、414 张图（最多的之一），但只有 2 个名字（仿身泪滴 / 黄金树看护者）。要么它真的是最常见的杂兵，要么它跟 `c0000` 一样是某种共用的缺省 —— **用之前建议先在游戏里看一眼**。
